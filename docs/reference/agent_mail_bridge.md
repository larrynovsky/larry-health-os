# Мост почты агентов: протокол каталога

Жанр: справочник. Единственный дом договора между мостом на хосте Studio (`scripts/agent_mail_bridge.py`) и health-процессом тенанта (`agent_mail.py`). Почему мост, а не почтамт внутри контейнера, — план нити agent-post, этап 1.1 (в закрытой части проекта); коротко: почтамт не удостоверяет отправителя (`post.py::deliver` проверяет только «есть в книге»), и процесс с правом писать в его корень слал бы от любого агента.

## Кто где

| Сторона | Где исполняется | Что видит |
|---|---|---|
| мост | Studio, launchd хоста `com.larry.health.agent-mail-bridge`, раз в 60 с | каталоги тенантов из `private/agent_mail.yaml`, почтамт infra (`post.py`, `addresses.yaml`) |
| health владельца | контейнер `health-bot-1` | `<HEALTH_DATA_DIR>/agent_mail` — туда смонтирован `~/agent_mail/owner` хоста (`scripts/install.py::render_owner_override`) |
| health партнёра | нативный процесс на Studio | `<HEALTH_DATA_DIR>/agent_mail` — обычная папка хоста |

Правило для health одно: каталог почты = `<HEALTH_DATA_DIR>/agent_mail`; `AGENT_MAIL_DIR` — только для тестов.

Соответствие тенант → адрес агента — `private/agent_mail.yaml` (приватная зона: имена тенантов) (единственный дом). Health адреса отправителя не выбирает и не пишет: отправителя ставит мост по каталогу.

## Каталог тенанта

```
<dir>/out/<id>.json      заявка на письмо (пишет health; tmp + rename)
<dir>/sent/<id>.json     квитанция отправки (пишет мост; заявка из out/ удаляется)
<dir>/in/<key>.json      входящее письмо (пишет мост после post read)
<dir>/ack/<key>          «показано человеку» (пишет health; пустой файл)
<dir>/acked/<key>        мост выполнил post ack (переносит из ack/)
<dir>/alive              время последнего прохода моста, unix-секунды текстом
```

`<id>` — `[0-9a-f]{32}`; `<key>` — номер письма почтамта (`post inbox`): `[0-9a-f]{24}`, sha256 от Message-ID и адресата (`post.py::_key`; живой пример 05.11 — `f68d6d2b727a1a18383a7ce5`). Имена другого вида мост игнорирует и пишет тревогу.

### Заявка `out/<id>.json`
```json
{"to": ["assistant-example"], "subject": "…", "body": "…", "reply_to": "<Message-ID>|null", "kind": "probe|state|lab_due|regimen|answer|task|nudge"}
```
Поля `from` нет. Если оно есть — мост отвергает заявку (`refused: from_field`).

### Квитанция `sent/<id>.json`
```json
{"id": "…", "message_id": "<…>", "statuses": {"assistant-example": "delivered"}, "refused": null, "at": 1730000000}
```
`refused` — причина отказа моста до почтамта: `foreign_owner` (адресат другого хозяина), `unknown_rcpt`, `from_field`, `bad_json`, `too_long` (тело > 8000 символов). При отказе `statuses` пуст. Статусы почтамта — как в `post.py`: `delivered | held | undelivered | rejected`.

### Входящее `in/<key>.json`
```json
{"key": "…", "message_id": "<…>", "from": "assistant-example", "subject": "…", "auto_submitted": false, "wrapped": "<письмо …>…</письмо>…", "at": 1730000000}
```
`wrapped` — вывод `post read` дословно (обёртка «данные», правило хозяина). Письмо с `Auto-Submitted` (квитанции почтамта) мост подтверждает сам и в `in/` не кладёт.

## Гарантии и их пределы

- Отправитель письма — только адрес тенанта каталога. Проверка — мутация «мост берёт from из заявки» краснеет.
- Адресат — только агент того же хозяина по `addresses.yaml`. Книга не читается → ни одной отправки (fail-closed).
- После `post read` письмо уже в `cur/` почтамта: потеря возможна только между `read` и записью `in/`. Мост пишет `in/` атомарно сразу после `read`; датчик `check_agent_mail_unacked` ловит прочитанные почтамтом и не подтверждённые.
- Health подтверждает (`ack/`) только после квитанции доставки человеку.

## Просроченные дела: локальный запасной путь (2026-11-07)

Основание — переданный владельцем результат **живого замера Claude 07.11.2026**
на Studio, `~/agent_post/post.sqlite`, таблица `letters`: кому ассистенту владельца — 22
`woken`, 0 `accepted`; ответы от ассистента с `parent` — примерно на половину
писем; на task-письма 07.11 в 08:45 и 10:37 ответов нет. Этот замер здесь
самостоятельно не повторялся. Ассистент не ставит ack; молчание нормально.
Поэтому отсутствие принятия не используется как авария и не порождает дубль
переписки. Ранее предложенный опрос `post status` удалён; протокол моста не меняется.

`task_route.hand_over` передаёт локальные `task_ids` в `agent_mail.send`.
Метаданные пишутся в `agent_mail.detail` до публикации заявки, поэтому сбой
транспорта не стирает связь. В wire-заявке этих новых метаданных нет.
`agent_mail.task_handover_times()` читает первое время заявки по каждому ID;
повторная передача не омолаживает дело. Старые записи без task_ids не угадываются.

`task_route.overdue_assistant_tasks()` при `tasks.route=assistant` выбирает только
переданные открытые дела с пустым `followup_sent_at`. Вопросы и анкеты исключены.
Для дела с ISO-датой deadline ждём конец этого дня в UTC и затем
`tasks.assistant_overdue_grace_days` полных дней (дефолт **2**).
Например, срок 7 ноября → кандидат с 10 ноября 00:00 UTC.
Без deadline ждём больше `tasks.assistant_no_deadline_days` суток от первой
передачи (дефолт **14**). Оба дефолта заданы по одному разу в коде; конфиг
читается через config_db. Значения — конечные целые дни, grace ≥0, ожидание ≥1.
Это инженерные интервалы внимания, не медицинские нормы: два дня оставляют
запас для организации дела, две недели ограничивают бессрочное зависание без
ежедневного шума. Наличие ack/ответа не меняет отбор. Закрытие любым путём,
включая «задача #N: сделано», исключает дело.

Существующий часовой `task_nudge_job` независимо от успеха `nudge` доставляет
сводки через прежние format_open_tasks_message, task_keyboard и send_long.
Партии до 20 задач отдельно для дел с датой и без даты. i18n-подписи:
«срок прошёл, ассистент не отметил выполнение» и
«срок ожидания прошёл: у дела нет даты, ассистент не отметил выполнение».
После квитанций всех частей ставится существующая followup_sent_at через
health_db/tasks_db. Просрочка не вызывает notify.fault: в обычном логе только
счётчик доставленных задач. Реальные ошибки конфигурации, БД и доставки
по-прежнему записываются как ошибки. Файл task_overdue.lock рядом с БД
сериализует проходы, почтовый каталог для запасной доставки не требуется.

Новых колонок/миграции схемы, сервисов, планировщика и зависимостей нет.
Развёртывать нужно только health; обновление host bridge не требуется.
**История без task_ids требует отдельного восстановления по исходным письмам
или решения о разовой доставке старых открытых дел.** Не связывать по времени.
При откате новые JSON-поля безвредны, а запасной путь исчезает.
Между отправкой в Telegram и отметкой нет общей транзакции: crash или
неоднозначный сетевой ответ допускает повтор; exactly-once не заявляется.
