# Git architecture: single canonical Studio

> **Тип документа:** Explanation (Diátaxis) — объясняет **почему** так, а не как делать.
> Конкретные команды: [docs/how-to/git_workflow.md](../how-to/git_workflow.md).
> Текущее состояние: CLAUDE.md § C «Среда» (в закрытой части) — норма; [docs/how-to/git_workflow.md](../how-to/git_workflow.md) — команды.

---

## Что было до 2026-05-09

Два независимых git-репозитория — на MacBook (`~/health_scripts/.git/`) и на Studio (`~/health_scripts/.git/`) — синхронизировались через `rsync` файловой системой. Git каждой машины не знал о существовании другого: для него своя `.git/` была единственным источником правды.

Это работало почти, пока совпадали HEAD'ы. Но обе машины делали **независимые auto-commits в 03:00** через `backup.sh`. Контент почти одинаковый (синканые файлы), но git создавал две разные SHA — у каждой машины своя «история того же дня». За месяц расхождение копилось до десятков параллельных commits.

В терминах распределённых систем (Tanenbaum §7) это была **active replication**: каждая «реплика» (машина) автономно применяла одну и ту же операцию. Active replication даёт **availability** (любая машина пишет в любой момент), но платит ценой **divergence** — без координации истории расходятся.

К 2026-05-09 разрыв стал болезненным: я (Claude) сделал ряд правок в течение дня, и не было однозначного ответа на вопрос «какой commit считать каноном» — MacBook 12:21 (`6fb6fc6`) или Studio 03:00 (`b785a88`)?

## Что стало после 2026-05-09

Studio объявлен **single canonical primary** для git. На MacBook `.git/` удалён. MacBook теперь — **read-only working copy**: файлы редактируются здесь, синкаются на Studio через doc-sync (для `.md`) или явный `rsync`/ssh (для `.py`). Все commit-операции происходят только на Studio.

В терминах §7.2 это переход от active replication к **primary-backup protocol**: одна машина (Studio) обладает правом записи, остальные могут только читать. Это сокращает availability (нельзя коммитить если Studio offline), но устраняет divergence как класс проблем.

## Что стало после 2026-05-23 (Sprint 7-GIT)

Опыт Sprint 6 показал: «MacBook без `.git/`» нарушалось де-факто. `.git/` восстановлен на MacBook 2026-05-23 (после поломки), и я (Claude) сделал 17 commit-ов с MacBook за день. `post-commit` hook делал `rsync --exclude='.git'` — файлы доехали на Studio, history осталась только на MacBook. Studio HEAD отстал на весь Sprint 6 (17 commits лежали как uncommitted в working tree). Потребовался ручной фикс через rsync `.git/` (опасная операция).

**Архитектурный вывод:** «MacBook без `.git/`» — неустойчивая инвариант. Local git-история нужна AI-помощникам (refactor batches, `git status`/`log` без ssh round-trip), и попытки её запретить заканчиваются восстановлением «нелегально». Лучше легализовать MacBook git как клон Studio и явно настроить sync через push protocol.

Новая модель — **Studio как git remote, MacBook auto-pushes**:

- MacBook имеет `.git/` (cloned from Studio).
- На Studio: `git config receive.denyCurrentBranch=updateInstead` — push в checked-out branch разрешён, working tree обновляется автоматически после fast-forward.
- `git remote add studio <studio_ssh>:~/health_scripts` на MacBook.
- `post-commit` hook на MacBook делает `git push studio main` (вместо `rsync --exclude='.git'`).
- `backup.sh` (ежедневный 03:00 auto-commit) делает `git commit + git push studio` локально на MacBook.
- ssh-edit на Studio по-прежнему разрешён (правило CLAUDE.md §1). После ssh-edit + commit на Studio — следующая сессия с MacBook начинается с `git fetch studio && git reset --hard studio/main` (или `bash scripts/sync_from_studio.sh`).

**Что это даёт:**

- Git как протокол sync — fast-forward check защищает от затирания. Push fail-fast при divergence (MacBook отстал от Studio); ошибка попадает в `logs/deploy.log`, bot не перезапускается на устаревший код.
- Атомарность: `git push` либо успешен полностью, либо нет вообще. `rsync .git` мог застрять на середине из-за `.git/index` lock.
- Studio working tree обновляется автоматически через `updateInstead` — без отдельного `rsync`-шага для файлов.
- `dirty working tree` на Studio в момент push → `updateInstead` отказывается. Это правильный сигнал: кто-то редактирует Studio ssh-edit'ом, надо подождать commit на Studio + pull на MacBook.

**Что мы получаем структурно:** Studio остаётся **canonical** в смысле «единственный production-инстанс» (бот, БД, scheduled jobs живут только тут). MacBook — **полноценный клиент**, не лишённый VCS. Авторитет распределяется так: новый код может приходить с обеих машин, но Studio имеет финальное слово через fast-forward check.

В терминах Tanenbaum — это **multi-master с pessimistic conflict detection через fast-forward invariant**, не полный multi-master (нет автоматического merge). Дивергенция возможна теоретически (одновременные commits на обеих машинах), но на практике редка: ssh-edit на Studio AI делает только когда явно нужно (например, восстановление git'а). Обычный flow — Edit на MacBook → commit → auto-push.

## Что мы получили

**Устранены классы багов**:

- Параллельные auto-commits с одинаковым контентом и разными SHA (раньше: каждый день +2 дублирующих commit).
- Невозможные merge-конфликты при попытке свести два дерева, у которых ancestor — двухнедельной давности.
- Вопрос «какая история каноническая» для критических документов (BLUEPRINT, ARCH_SNAPSHOT, USE_CASES) — теперь однозначный.

**Получили линейную историю**: каждый commit имеет одного родителя, что даёт работающие `git bisect`, `git blame` и осмысленный `git log`.

## Что мы потеряли

**Availability при offline Studio**. Если Tailscale упал или Studio выключен — `backup.sh` на MacBook логирует `WARN: ssh trigger failed`, и commit не делается. На следующий день при возвращении связи commit пройдёт нормально. Это приемлемо: Tailscale у нас стабилен, и потеря одной auto-commit-точки — не катастрофа (правки лежат в файлах, не теряются).

**Локальный git blame на MacBook**. После удаления `.git/` редактор на MacBook не показывает git history. Если нужен blame — через ssh: `ssh studio "git -C ~/health_scripts blame файл.py"`. Для повседневной работы это редко нужно.

**Простой откат через `git checkout` на MacBook**. Откат нужно делать на Studio: `ssh studio "git checkout HEAD~ -- файл.py"` и потом `rsync` обратно на MacBook (или ждать doc-sync для `.md`).

## Какие альтернативы рассматривались

**Альтернатива A: оставить два репо, регулярно мержить.** Отвергнута — каждый день +2 commit'а расхождения, через год — 700 ненужных merge-commits.

**Альтернатива B: сделать MacBook источником, Studio — зеркалом.** Отвергнута — Studio выполняет production-задачи (бот, API, тесты), и нет архитектурной причины давать MacBook авторитет в git.

**Альтернатива C: bare-repo на третьей машине + push/pull с обоих.** Отвергнута как избыточная сложность. У нас один пользователь, не команда.

> **Допущение «не команда» устарело (2026-09-11).** Пользователь по-прежнему один, но параллельных нитей — пять и больше, и для git это неотличимо от команды: одновременные писатели, конкуренция за деплой-канал, работа, которую нельзя смешивать в один коммит. Решение при этом НЕ меняется: bare-repo на третьей машине не понадобился, зазор закрыт дешевле — своё дерево на нить (§1 протокола мультисессии) плюс guard ветки в post-commit. Запись здесь стоит не ради смены решения, а потому что обоснование пережило бы свой предмет молча (§18): следующий читатель принял бы «не команда» за действующий факт и отверг бы по нему что-нибудь ещё. Цена нынешней схемы названа там же: деплой из ветки не идёт, и тишина больше не означает успех.

**Альтернатива D (выбрана): Studio как single canonical, MacBook без `.git/`.** Минимальная сложность, нулевая дивергенция.

## Совместимость с правилом single-primary для БД

Правило БД (CLAUDE.md §8, введено 2026-04-24): **Studio — единственный primary для health.db**. После миграции git — Studio также единственный primary для git-репо. Оба правила следуют одной архитектурной идее: **одна машина — одна ответственность за каждый ресурс, MacBook = клиент**.

В терминах Tanenbaum это уменьшает **conit numerical deviation** до нуля для обоих ресурсов.

## Восстановление после катастрофы

Если Studio погибнет окончательно (SSD, кража, etc.):

1. Time Machine содержит снимок `~/health_scripts/` включая `.git/` — восстановление git-истории через TM.
2. Параллельно: bundle от 2026-05-09 (`/tmp/macbook_health_v2.bundle`) хранится локально на MacBook — последний backup git-истории до миграции.
3. iCloud-копия БД устарела с 2026-04-24 (по single-primary правилу) — для восстановления данных нужен Time Machine.

Если MacBook погибнет — потери минимальны: рабочая копия восстанавливается через `rsync <studio_ssh>:~/health_scripts/ ~/health_scripts/`.

## Урок миграции 2026-05-10

После reset --hard на MacBook canonical contract-test поймал regression: `morning_test_summary.py` снова имел 7-параметровую сигнатуру `save_agent_report` вместо 12. Корень: фикс W2C-2 был сделан **только** через ssh-патч на Studio, на MacBook не доехал (`.py` не синкается через doc-sync, явный rsync обратно на MacBook никто не делал). Bundle для миграции собирался с MacBook → ssh-only фиксы в нём отсутствовали → reset --hard их физически выкинул из Studio working tree.

То же касается `run_full_test_suite.sh` (W2C-3 case-map для snapshot-слоя).

**Что важно для будущих миграций**:

1. **Перед любым reset --hard на старый commit** — сравнить md5 критичных `.py` и `.sh` на обеих машинах. Если различаются — на MacBook есть устаревший код, в Studio — актуальный, который потеряется при reset.
2. **Стратегия**: до bundle-сборки на MacBook сделать обратный rsync `studio:~/health_scripts/*.py → MacBook`, потом commit «sync: ssh-only edits from Studio» на MacBook, потом bundle. Так свежий Studio'й код попадёт в bundle.
3. **После любого reset --hard** — прогнать `pytest tests/unit/test_save_agent_report_contract.py` и весь suite до commit'а merge. Эта проверка стоит 5 секунд и ловит ровно этот класс багов.

Эта дисциплина закрепляется в Wave 3-DOC P1-3 как T-P1-А. Сегодняшняя regression подтверждает ценность contract-test, который и был создан 2026-05-09 именно для класса BUG-AGENTREPORTS-SIG. Тест поймал свою же предтечу.

## Незакоммиченная работа: кто её защищает и кто её видит (2026-09-07)

Переезд 23.05 сделал MacBook местом, где пишут код, а Studio — деплой-таргетом. У
этого переезда был тихий побочный эффект, замеченный только сейчас.

`uncommitted_watchdog` построен 17.05 под класс «работу написали и не закоммитили,
обнаружили через сутки регрессиями». Тогда код писали на Studio, и «забытый коммит»
с «грязным деплой-таргетом» были одним и тем же деревом. После 23.05 это два разных
дерева на двух машинах — а сторож остался на Studio. Он по-прежнему нужен и ловит
реальное (правку по ssh мимо MacBook, неудавшийся push, конфликт `updateInstead` —
инцидент 05.07: 25 часов грязи), но исходный класс уехал вместе с работой и полтора
месяца не был покрыт ничем, кроме суточного снимка `backup.sh`. Заметить это стоило
одной проверки `launchctl` на MacBook — и она не делалась, потому что докстринг
сторожа уверенно говорил, что он сторожит именно это (§18: утверждение пережило свой
предмет).

Починено с двух сторон.

**Защита — чаще.** `backup.sh --wip` снимает рабочее дерево каждые три часа
(launchd `com.larry.health.backup-wip`, MacBook-only) в один перекатывающийся
`refs/backups/wip` и пушит его на Studio. Окно потери несохранённой работы: было
≤24 часов, стало ≤3. Суточные `refs/backups/daily-*` и их ротация 14 остались как
были — они ведут историю, wip ведёт свежесть. Механизм тот же самый: снимок во
временном индексе → `commit-tree` → ref вне `main`; ни деплоя, ни обхода гейтов.

**Наблюдение — со всегда включённой машины.** `integrity_tests
.check_macbook_uncommitted` сравнивает свежайший снимок с его родителем: всё, что не
в `git_facts.MACHINE_REGENERATED_FILES`, — незакоммиченная работа человека. WARN
класса `decide`, то есть строка в утренней доставке, а не FAIL: коммитить или нет —
решение владельца (§13).

**Почему сторожа НЕ поставили на ноутбук.** У ноутбука не может быть честного сигнала
живости: он законно спит, ездит и стоит с закрытой крышкой, и изнутри «сторож умер»
неотличимо от «крышка закрыта». Датчик, чьё молчание означает и то и другое, нарушает
§14 по построению. Зато Studio всегда включён и уже видит дерево MacBook — снимок
приезжает сюда сам. Поэтому судим артефакт, а ноутбук ни о чём не спрашиваем.

**Что этот фильтр стоил и что он прячет.** Без фильтра деривативов датчик был бы
чистым шумом: замер по 14 хранящимся снимкам (07.09) — сигнал в 14 днях из 14, потому
что `doc_agent` стейджит `CHANGELOG.md`/`ARCH_SNAPSHOT.md` после КАЖДОГО коммита, а
`arch_guard` переписывает `.arch_graph.json`. С фильтром — 2 из 14, и оба попадания
настоящие: 30.07 (пять файлов работы) и 04.08 (правка `CLAUDE.md` руками). Цена
названа честно: фильтр по ИМЕНИ, а не по авторству, поэтому ручная правка
`CHANGELOG.md` датчиком не увидится.

**Что осталось непокрытым, вслух.** Устаревший снимок не различает «ноутбук выключен»
и «джоба снимка мертва» — отсюда это неразличимо в принципе, поэтому текст варна
называет оба чтения, а порог держится высоким (3 суток), чтобы выходные не звенели.
И `com.larry.health.backup-wip` не входит в ценз `producer_registry`: тот обходит
launchd машины, на которой бежит integrity, то есть Studio, а эта джоба — на MacBook.
Ценз машин, отличных от Studio, в проекте не построен вообще.
