# Тестовая архитектура

> **Тип документа:** Explanation (Diataxis) — объясняет, **почему** тестовая
> система устроена именно так. Для **что есть** — см. `TEST_ARCHITECTURE.md`,
> `USE_CASES.md`, `uc_index.yaml`. Для **как делать** — см.
> `docs/how-to/run_tests.md`, `add_new_uc.md`, `handle_test_failure.md`.

---

## Идея

Health OS делает медицинские утверждения. Тесты должны ловить **регрессии в
правильности этих утверждений**, не только «код не падает». Это меняет всё
относительно стандартного pytest-каркаса.

## Три ключевые установки

### 1. Spec-by-example: `USE_CASES.md` — единственная точка истины

Каталог UC описывает **желаемое поведение**, не текущее. Тест против
`intended` UC — это `expected_gap`, не «сломанный тест». Тест против
`implemented` UC — это regression-сигнал.

`status` × `confirmation` lifecycle различает:

| status | confirmation | failing test означает |
|---|---|---|
| `implemented` | `confirmed` | REGRESSION → CRITICAL → TG-алерт + Reminder |
| `partial` (gap-часть) | `confirmed` | expected_gap → INFO |
| `intended` | `confirmed` | expected_gap → INFO (код ещё не догнал намерение) |
| любое | `proposed`/`rejected` | тест не должен существовать (UC-J-02) |

Без `confirmation = confirmed` `generate_test.py` отказывается генерировать
скелет — это disciplined development.

### 2. Граница автоматизации: B+E+C+D, плюс H для качества

Не всё медицинское качество автоматизируется. Стратегия из 4 уровней:

- **B (negative invariants)** — что система НЕ должна делать. Главный
  инвариант для медицины: «если NULL — не утверждай».
- **E (cross-check с детерминированной правдой)** — числа в тексте = числа
  в БД (не выдуманные).
- **C (snapshot)** — для критичных JSON-структур. Для LLM-output **отвергнут**
  как иллюзия защиты (не различает «регрессия в коде» vs «LLM-нестабильность»).
- **D (LLM-judge)** — отдельный Claude Haiku с явными вопросами. Не источник
  правды. Никогда не единственный оракул для P0.

Для качественных утверждений (UC-I-08 онкоконтекст, UC-I-09 геном-как-рамка,
UC-H-03 Round B deliberation) — `H` (Human charter): риск-ориентированный
маршрут ревью. Это не код, а markdown в `tests/charters/`. `assert "хороший
врач"` не существует.

### 3. Распределённые свойства Health OS требуют отдельного слоя тестов

Стандартная test pyramid игнорирует то, что в проекте есть:

- **Conit + staleness deviation** (TC §1) — данные старше 26ч/30 дней
  должны срабатывать алерт. Тесты на это требуют **подмены времени**, иначе
  они нереализуемы. `_time_inject.py` решает это централизованно.
- **Tentative-запись** — `pending_labs/` это отдельный наблюдаемый объект
  ДО approval. Тест переход tentative → committed.
- **Single-primary** — write в `health.db` только с Studio. Guard в
  `health_db.get_conn()` возвращает read-only коннект на не-Studio.
- **Read-your-writes** — checkin вечером → GP видит утром.
- **Causal consistency** — Council Round B зависит от Round A.
- **Eventual consistency** — Tasks ↔ Reminders sync window 3ч.

Для них есть отдельный слой `tests/consistency/` (не unit, не integration —
именно про распределённые свойства).

## 7-слойная пирамида

```
                    Charter (H)            5 шт   ← markdown, не код
                  Snapshot (C)            ~1 шт   ← минимально
              LLM-judge (D)               2 шт    ← skipped без API ключа
          Consistency-specific           21 шт    ← RYW/tentative/staleness/...
        E2E_mock                          5 шт
      Integration                        14 шт
    Unit                                 ~110 шт  ← основа
```

Слои 1-4 запускаются на каждый коммит через `pytest -m "not slow"`.
Слой 5 (consistency) тоже быстрый, в основной набор.
Слой 6 (LLM-judge) — только nightly, требует Anthropic API.
Слой 7 (charter) — не код, по календарю.

## Архитектурные решения, которые требовали обоснования

### Почему `_time_inject.py`, а не параметр `clock` в каждой функции

Изначальный план был «опциональный `clock` параметр в важных функциях».
После аудита выяснилось: 40+ файлов используют `date.today()` /
`datetime.now()`. Параметр в каждой — это много церемонии в коде агентов
и легко забыть передать в одном из мест.

`_time_inject.get_now()` / `get_today()` — глобальная подмена через
`set_test_clock()`. Тест меняет `_TEST_CLOCK`, прод видит реальное время.
В тестах автоматический сброс через autouse fixture в `conftest.py`.

CLI-блоки `if __name__ == "__main__":` намеренно не тронуты — тест вызывает
функцию напрямую с фикс-датами, минуя CLI.

### Почему snapshot для LLM-output отвергнут

Snapshot ловит расхождение с эталоном. Но для LLM расхождение может быть
от: (а) регрессии кода, (б) нестабильности модели, (в) нормальной
вариативности генерации. Snapshot не различает.

Замена для UC-A-01 (`lab_extractor`): self-consistency — двойной прогон на
одном PDF, ключевые поля `{name, value, unit, flagged}` должны совпадать
бит-в-бит. Расхождение = нестабильность extractor-а (actionable: нужен
рефакторинг промпта или temperature=0). Это не рукопашная битва с
эталонами при каждом изменении.

### Почему test_failure_handler не чинит код сам (Repair сужен, см. поправку ниже)

Полностью автоматический Claude-патчинг прод-кода в медицинской системе =
риск тихих ослаблений ассертов. Claude в агентном режиме иногда «починит»
тест, ослабив проверку, вместо того чтобы чинить логику. Цена тихой
регрессии правильности медвыводов выше любой экономии времени.

Принятая модель: **diagnose, don't repair**.
- Уровень A — детерминированные ретраи по паттернам логов.
- Уровень B — Haiku пишет diagnosis в markdown, человек читает утром.
- Reminder на 10:00 с готовым промптом для копипаста — твоя идея, оказалась
  здравой. Утром: открыл Reminder → скопировал → Claude помог разобраться.

**Поправка владельца 2026-08-03 (нить night-cycle): запрет СУЖЕН, а не снят.**
Авто-применение красного разрешено при всех трёх условиях одновременно:
(1) действие обратимо (`git revert`, не удаление строк и не миграция данных);
(2) патч прошёл независимого агента-ревьюера (§17 — промпт на опровержение,
без авторских объяснений); (3) есть краснеющий ВНИЗ ПО ПОТОКУ оракул — ночной
integrity ловит поломку ОТ фикса и паркует обратно. Всё остальное — по-прежнему
«diagnose, don't repair». Нормативный текст и цена, принятая владельцем зряче
(окно до суток между применением и ночной ловлей), — в своде, `CLAUDE.md §13`;
здесь — указатель, чтобы страница не читалась как действующий полный запрет.
Носитель-механизм (`fix_applier`) не построен: до него поправка декларативна.

### Почему severity по статусу UC, а не по типу теста

Подход «упал тест → CRITICAL» создаёт шум. 70% тестов могут быть на
`intended` UC, и каждый ночной прогон будет CRITICAL.

Подход «упал тест → CRITICAL зависит от status UC» отделяет регрессии от
expected_gap. Если UC-A-01 имеет status=`partial` (Council автозапуск
отложен в backlog), тест на эту часть пайплайна — `expected_gap`, не шум.

### Почему UC-J-02 запрещает генерацию теста для unconfirmed UC

Без этого процесса агент мог бы написать тест на свою интерпретацию UC,
вместо того чтобы выяснить с пользователем что именно тестируется.
`confirmation = confirmed` — это явный gate: «да, это поведение мы
тестируем».

### Почему запрещён `sys.modules.pop`/reload общих модулей в тестах (2026-06-22)

`health_db` импортируют десятки модулей (`treatment_*`, `survivorship`, и т.д.).
Если фикстура делает `sys.modules.pop("health_db")` + reimport, создаётся НОВЫЙ
объект модуля. Уже импортировавшие старый держат v1, а fixture/тест работают с
v2 → **split-brain двух health_db**: записи идут в одну БД, чтение из другой.
Симптом коварен — тест проходит в одиночку, падает только в полном прогоне
(`pytest tests/`), причём в НЕ связанных файлах, и зависит от порядка коллекции.
Так весь `tests/` молча был красным (22 failed) при зелёных под-сьютах.

Правила:
- подмена БД — через `monkeypatch.setattr(health_db, "DB_PATH", tmp)` (тот же
  объект, авто-restore), как в `tests/fixtures/db.py`. Не pop+reimport.
- если pop неизбежен (тест import-time guard'а): сохранить ОРИГИНАЛЬНЫЙ объект и
  вернуть ровно его в `finally`, не свежий import. `importlib.reload(x)` мягче —
  re-executes in place, идентичность сохраняется.
- диагностика порядко-зависимых падений — бисектом (подозреваемый файл ПЕРЕД
  жертвой), не по интуиции «модули не связаны».

⚠️ `run_checks.sh` (post-commit) гоняет smoke_tests + integrity_tests, НЕ pytest —
этот класс багов ловится только ручным/CI полным `pytest tests/`.

В медицинской системе цена «написал тест на не то поведение» = regression
не ловится → плохие выводы доходят до пользователя.

### Почему тест ждёт свои потоки до разборки фикстур (2026-10-05)

Подмена базы в тесте (`monkeypatch`, временный `DB_PATH`) живёт ровно до разборки фикстур.
Поток, запущенный тестом, о ней не знает: если он работает дольше теста, его поздняя запись
идёт по пути, который уже вернули на место. Ночью этот путь — живая база владельца.

Так и было с 30.08 по 04.10. Тест фонового консилиума ждал *вызова* консилиума, а не конца
работы потока. Поток дописывал вердикт в живую базу — в строку `memory` с тем же номером, что у
гипотезы в тестовой базе (номер общий у всех категорий), — и создавал по полю `test` задачи
владельцу. Тест был зелёным. Остановил запись сторож `query_only` (нить treatment-homes), но и
тогда в ночном журнале осталась одна строка предупреждения, которую никто не читал.

Что стоит теперь (tests/conftest.py, блок `thread_guard`; pytest.ini):
- хук фазы вызова ждёт потоки, рождённые тестом, — в фазе вызова, то есть ДО разборки фикстур;
  фикстура так не может: её разборка шла бы после отката подмены;
- не дождались — тест красный с именем потока;
- исключение в потоке — ошибка, а не предупреждение (`filterwarnings`);
- граница: простаивающий рабочий пула AnyIO (TestClient панели) исключён по имени — ответ к
  этому моменту отдан; замер стенда: 69 тестов панели краснели только на нём;
- решатель гипотез пишет только в строки `category='hypothesis'`.

**Ночной набор остаётся на живом окружении (06.10.2026, решение владельца).** Прогон на копии
базы замерили: копия в другом каталоге ломает ~60 тестов, сверяющих каталог данных с установленными
службами, и даёт каскад ошибок фикстур. Поэтому ночь идёт под сторожами выше, а не на копии.
Рабочий пула AnyIO исключается из сторожа потоков по классу и простою (очередь `idle_workers`),
а не по имени: занятый рабочий ждётся как любой поток.

Ночная хроника (`run_checks.sh`) называет по именам и ERROR (сбой фикстуры или разборки), а не
только FAILED: красная сторожа в фикстуре иначе прошла бы мимо как «набор не изменился».

## Контракт-тесты публичных API (паттерн, валидирован 2026-05-10)

Шаблон, который оказался ценным после regression 2026-05-10:

**Идея**. Если публичная функция в `health_db.py` (или другом core-модуле) имеет required-параметры, у неё **N caller'ов** в коде. При изменении сигнатуры один из caller'ов может остаться с устаревшим вызовом. Если caller вызывается редко (раз в сутки в 03:00) — баг проявится не сразу. Если crash silenced через `try/except` (как было в `morning_test_summary.save_to_db`) — может молчать неделями.

**Шаблон теста** (см. `tests/unit/test_save_agent_report_contract.py`):

1. AST-парсер сканирует все `*.py` в проекте.
2. Находит вызовы `<func_name>(...)` (по имени или через `db.<func_name>`).
3. Для каждого вызова: собирает `args` (positional) + `keywords` (kwargs).
4. Сравнивает с `inspect.signature(func)` для required-параметров.
5. Падает с указанием `файл:строка` и списком missing args.

**Когда применять**:

- Публичные API, у которых `≥2` caller'ов в проекте.
- Сигнатура содержит required-параметры (без default).
- Caller'ы вызываются нечасто или через `try/except`.

**Ценность**: проверка занимает ~100мс, ловит class-wide регрессию за один день, а не за неделю расследования. После эпизода 2026-05-10 (reset --hard вернул morning_test_summary к 7-args сигнатуре, contract-test поймал в первую же ночь) этот паттерн валидирован практикой.

**Экспансия**: после `save_agent_report` стоит покрыть остальные публичные функции `health_db.py` с required-args. Это W3-DOC-расширение, не одноразовая работа.

**Лимиты**:

- Не ловит **семантические** регрессии (caller передал правильное число args, но в неправильном порядке) — это работа `inspect.signature` + named-only args в коде.
- Не ловит регрессии **через косвенный вызов** (`getattr(db, name)(...)` где `name` runtime-определён). Этот класс редок в проекте.
