# Backup Policy — health.db

> Урок 2026-06-27: pgs_discovery.py без лимитов → WAL 31GB → коррупция DB.
> Восстановление из 9-дневного бэкапа стоило ~4 часа работы.
> Этот документ фиксирует правила, которые делают такой разрыв невозможным.

---

## Модель

Бэкап — это реплика с **staleness deviation** (временным отклонением).
Допустимое отклонение = то, сколько работы мы готовы потерять и воспроизвести заново.
При текущей системе: каждый день накапливается ~30 мин восстанавливаемой работы
(Oura, GP-отчёт) + нерегулярные операции (конституции, consilium) от 15 мин до 2 часов.

**Staleness SLA = 24 часа** — то есть ни одного пропущенного ночного прогона: с 23.09 датчик
судит «свежайший бэкап не старше последнего планового запуска `com.larry.health.backup` по
живому плисту» (решение владельца «общее правило»: тревога после первого пропуска).

---

## Правила

### R0 — Разделение по ответственности машин (2026-05-09, после BUG-BACKUP-DEAD)

Каждая машина бэкапит то, в чём она authority. Две джобы `com.larry.health.backup`, обе в 03:00, делают РАЗНОЕ:

| Машина | Скрипт | Что бэкапит | Куда |
|---|---|---|---|
| **Studio** | `backup_studio.sh` | `sqlite3 .backup` для `~/health/data/health.db` (production) и `<neighbour>/<db>.db` | `~/health/backups/`, `<neighbour>/backups/`, ротация 30 дней (R1) |
| **MacBook** | `backup.sh` | снимок КОДА: дерево во временном индексе → `commit-tree` → `refs/backups/daily-<дата>` → `push -f` на Studio | локально 14 последних снимков; БД не трогает и никогда не трогал |

Тенант, переехавший в контейнер (пилот волны Б, метка `RUNTIME` со словом `container` в корне его данных), нативным `backup_studio.sh` пропускается: его база живёт в томе контейнера, и бэкап делает задача контейнера (`~/health/backups` внутри тома), а раз в час снимок копирует на хост теневой сторож. Партнёр и соседний проект бэкапятся нативно, как прежде. ⟨carriers: backup_studio.sh, tests/unit/test_backup_skips_container_tenant.py⟩

Что MacBook-скрипт **не** делает с 2026-07-24 (решение владельца): не коммитит в `main` и не пушит `main`. Раньше делал `git commit --no-verify` + push — ночью деплоился непроверенный WIP, обходились все гейты (dupgate/L2/доки), история зарастала «auto: daily backup». Теперь снимок ≠ коммит в `main`: деплоя нет, гейты не обходятся, `main`/индекс/working tree не тронуты. Восстановление файла: `git checkout refs/backups/daily-<дата> -- <файл>`. Норма про незакоммиченное — `CLAUDE.md §1` (в закрытой части).

**Почему разделено — macOS TCC.** До 2026-05-09 `backup.sh` смотрел в iCloud-путь и **падал на authorization denied 35 ночей из 36** (единственный успешный бэкап — 2026-04-20): TCC блокирует `sqlite3` на `~/Library/Mobile Documents/` при запуске из launchd. Второй, независимый дефект той же конструкции: после 2026-04-24 (single-primary → Studio) iCloud-копия перестала быть operational, поэтому даже без TCC скрипт бэкапил не ту БД. Оба лечатся одним — база бэкапится там, где она канонична.

**iCloud-копия БД — НЕ бэкап** (решение 2026-07-02). `~/Library/Mobile Documents/.../health.db` — нерабочая копия: свежесть не гарантируется и не проверяется, рассчитывать на неё нельзя. Реестр всех точек контакта кода с iCloud — `icloud_contacts.yaml`, полноту реестра держит census-датчик `tests/integration/test_icloud_contact_registry.py`.

### R1 — Daily backup (автоматический)

`backup_studio.sh` запускается launchd (`com.larry.health.backup.plist`) каждый день в **03:00**.
1. `PRAGMA wal_checkpoint(TRUNCATE)` — сбрасывает WAL перед копированием
2. `sqlite3 .backup` — горячая копия (не блокирует читателей)
3. `PRAGMA integrity_check` — проверяет свежую копию сразу
4. Ротация: бэкапы старше 30 дней удаляются

Файл: `~/health/backups/health_YYYY-MM-DD.db`
Хранение: ~33 копии (30-дневное окно).

Проверка что backup job работает:
```bash
ssh <studio_ssh> "tail -5 ~/health/logs/backup.log"
```

Если самый свежий старше последнего планового запуска (сейчас — 03:00 сегодня) — job сломан.
Чинить немедленно.
`integrity_tests.py` [11] отловит это автоматически и пришлёт алерт в Telegram.

### R2 — Pre-operation snapshot (ручной, перед destructive run)

Перед любой операцией с неограниченным write-эффектом:
```bash
ssh <studio_ssh> "cp ~/health/data/health.db \
  ~/health/data/health.db.before_<operation>_$(date +%Y%m%d_%H%M)"
```

**Когда обязателен:**
- Запуск `pgs_discovery.py` (импорт PGS Catalog) — **автоматически** (см. ниже)
- Запуск `genome_annotator.py` (аннотация ClinVar) — вручную
- Запуск `vcf_import_pipeline.py` (полный VCF reimport) — вручную
- Любой скрипт, который делает массовый INSERT без явного лимита

`pgs_discovery.py` создаёт снимок автоматически перед Step 4 (import loop):
`~/health/backups/health.before_pgs_discovery_YYYYMMDD_HHMM.db`
через `sqlite3` online backup API (не `cp` — не захватывает открытый WAL).

**Когда не нужен:**
- `generate_constitutions.py` (пишет только в `constitutions`, не меняет raw data)
- `import_oura.py` (upsert по дате, идемпотентно)
- `fill_description_ru.py` (UPDATE по ключу, idempotent)

**Срок жизни снимка — 60 дней (R1b, решения владельца 2026-09-27).** Снимок нужен, чтобы
откатить акт, пока его последствия не проверены; дальше откат идёт из ежедневных бэкапов (R1,
30 дней). Утром 27.09 срок был поставлен 30 дней и только для каталога данных; днём владелец
решил «удалить сейчас и сделать правило 60 дней» — срок стал 60 и распространён на `backups/`.
До этого снимки жили вечно: замер 27.09 — 134 файла, 7 ГБ в каталоге данных владельца, 26 у
партнёра (BL-SNAPSHOT-SPRAWL-1), и ещё 16 ГБ в `backups/` (снимки справочника PGS по 5–10 ГБ
ежемесячно, июльские снимки партнёра по 3,8 ГБ). Удаляет их `backup_studio.sh` той же ночью, что
и старые бэкапы (`ACT_SNAPSHOT_DAYS`):
- `scripts/rotate_act_snapshots.sh <tenant>/data` — снимок узнаётся по устройству: SQLite-файл
  (кроме канона), файл с `.bak` в имени, всё в `<tenant>/data/backups/`;
- `scripts/rotate_backup_snapshots.sh <tenant>/backups` — снимок всё, кроме ежедневных
  `<tenant>_YYYY-MM-DD.db` (R1) и папки `<tenant>/backups/keep/`.
Имя можно давать любое. **Снимок, нужный дольше 60 дней, кладут в `<tenant>/backups/keep/`** —
осознанно, одним движением, и он остаётся, пока его оттуда не уберут.

### R2.5 — Оффсайта у БД НЕТ (замер 2026-08-02) ⚠️

`ssh <studio_ssh> tmutil destinationinfo` → **«No destinations configured»**; `tmutil latestbackup` → ошибка монтирования. Time Machine на Studio не настроен.

Значение: канон (`~/health/data/health.db`) и **все** 30 суток бэкапов (`~/health/backups/`) лежат на одном диске одной машины. Отказ диска Studio уносит и то и другое одновременно. R1 защищает от логической порчи (WAL, коррупция, ошибочный массовый UPDATE) и **не защищает от отказа носителя**.

Откуда взялось расхождение: 2026-05-09 принято решение «оффсайт делегирован Time Machine» (`BACKLOG_ARCHIVE.md:830`), решение НЕ исполнено, а пункт при этом ушёл в архив как закрытый — следить стало нечему. `BLUEPRINT` до 2026-08-02 повторял его как факт. Заголовок самого `backup.sh` («Оффсайт для БД пока не настроен») всё это время говорил правду, и никто их не сверял. Экземпляр `CLAUDE.md §18` (в закрытой части): утверждение о состоянии ВНЕ носителя, без счётчика и без даты.

Код лежит на двух машинах: клон на MacBook + `refs/backups/` на Studio. База — на одной.

**Поправка 2026-09-16, и она про то, что «две машины» было верно НЕ для всего кода.**
До 16.09 на двух машинах жил только `main`: `post-commit` пушит его и выходит до push,
если ветка другая («не main → выход ДО push» написано в самом хуке), а снимок брался с
главной копии. Значит закоммиченная работа нити от первого коммита до слияния
существовала в ОДНОМ экземпляре. Замер 16.09: 992 строки двух нитей (`close-rebase-once`
757 строк / 22 ч, `dead-root-loud` 235 / 62 ч), и `git cat-file -e` на Studio отвечал
«нет» для обоих tip'ов. Экземпляр `CLAUDE.md §18` (в закрытой части) в чистом виде:
утверждение о соседней машине без счётчика и без даты пережило свой предмет.
С 16.09 `backup.sh --wip` копирует ветки нитей в `refs/backups/thread/*` (namespace
инертный: `updateInstead` трогает дерево Studio только для checked-out ветки), а датчик
`check_thread_work_has_a_second_copy` судит НАЛИЧИЕ объекта на Studio, а не рапорт об
успешном push. Копия удаляется только ДОКАЗАННО доехавшая до `main` (предок либо то же содержание по `git cherry`) — решение владельца:
`git push --prune` удалял бы копию ветки, удалённой локально, а ветка исчезает и при
слиянии, и при потере дерева. Окно потери не ноль, а период снимка (3 ч).
С 21.09 закрытие нити переставляет ветку; если при этом содержание переписано, копия
не удаляется, а переносится в `refs/backups/thread-closed/<нить>` — данные остаются,
а список «работа в одном экземпляре» перестаёт засоряться закрытыми нитями.
Незакоммиченное в деревьях нитей не копируется по-прежнему: p90 интервала между
коммитами внутри нити — 11 минут, и снимок несёт `worktrees_uncovered=N` как честное
«про эти деревья не знаю». Замысел целиком — запись `code_backup` в `subsystem_intent.yaml`.

**Решение владельца 2026-08-13: риск принят явно, оффсайта не будет.** Прежний вариант A («внешний диск + Time Machine», 2026-08-03) вычеркнут; датчик `check_offsite_configured` удалён (`aec8173`). Пункт закрыт не исполнением, а осознанным принятием риска: отказ носителя Studio уносит канон и все копии разом, и с этой даты это стережёт только само это предложение. Передумаешь — новый датчик заводится вместе с новым решением, не раньше (§9: норма не раньше механизма).

### R3 — Integrity check перед использованием бэкапа

Восстанавливать только из бэкапа, прошедшего проверку:
```bash
sqlite3 /path/to/backup.db 'PRAGMA integrity_check'
# Должно вернуть: ok
```

Размер бэкапа должен быть разумным (< 500MB при текущем объёме данных).
Если больше — это признак незафиксированного WAL, не валидный бэкап.

## Антипаттерны (не делать)

- `backup.sh` без проверки exit code → тихий провал
- бэкап с открытым WAL (`cp` пока идёт запись) → невалидный файл
  → использовать `.dump` или `VACUUM INTO` для online backup
- хранить только один бэкап → нет возможности откатиться на 2 дня назад
- считать `integrity_check = ok` достаточным → не ловит WAL-corruption и size bloat
