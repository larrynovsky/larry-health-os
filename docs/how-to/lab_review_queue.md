# How-to: разобрать очередь ревью лабораторных строк

> Когда нужен: ночной триаж прислал `очередь ревью[health] не движется: N строк
> ждут человека Nд`. Датчик — `integrity_tests.check_lab_review_queue_movement`.
> Перед работой измерь текущую очередь (шаг 1). Состав и числа относятся
> к текущему прогону и не являются постоянной исходной точкой этого руководства.

## Что алерт означает и чего НЕ означает

Означает: в `lab_results_staging` есть строки со статусом `review`, и самая
старая из них ждёт дольше порога (`lab.review_stale_days`).

**НЕ означает «ты должен что-то решить по каждой».** Часть строк может
ждать только промоута или обновления статуса после уже применённого правила.
Отдели их от строк, которым требуется новое решение.

Статус `review` ставит `lab_triage.py:89`. **Снимает его только промоут** —
и только с тех строк, которые он реально берёт (`review_status='promoted'`,
`lab_promote.py:593`) или которые ты явно отклонил. Строка, которую промоут
блокирует, висит в `review` вечно: у неё нет двери на выход, пока имя не сведут
к канону или строку не отклонят. Поэтому очередь не рассасывается сама.

## Шаг 0. Если алерт про `pending`, а не про `review`

Второй алерт той же семьи — `staging[<тенант>]: N строк не классифицированы Nд`
(датчик `check_staging_status_coverage`). Это ДРУГАЯ очередь: строки, до которых
`lab_triage` ещё не дотронулся. Порядок:

1. **Сначала спец-слой, потом триаж.** Строки, чей класс по вердикту
   (`lab_domain_verdicts`) едет в `specialized`, получают терминальный статус
   `specialized` только от `lab_specialized.promote_specialized(run_id, execute=True)`.
   Триаж, запущенный первым, может отправить их в `review` как немаппированные
   аналиты, хотя назначенный им дом — спец-слой.
2. **Дрой триажа** — `lab_triage.triage(execute=False)` печатает корзины.
   Проверь строки и причины из `_classify`, особенно
   `rejected: физиологически невозможно`: сверь единицы и повторные конверсии,
   прежде чем принять отклонение.
3. `triage(execute=True)` — и дальше по шагам ниже уже для очереди `review`.

## Шаг 1. Перемерить (read-only, ничего не меняет)

```bash
ssh <studio_ssh> 'cd ~/health_scripts && /opt/homebrew/bin/python3.11 -c "
import sqlite3, collections, sys
sys.path.insert(0, \".\")
import lab_promote as lp
c = sqlite3.connect(\"file:~/health/data/health.db?mode=ro\", uri=True)
c.row_factory = sqlite3.Row
rows = [dict(r) for r in c.execute(
    \"SELECT * FROM lab_results_staging WHERE review_status=%s\" % repr(chr(39)+\"review\"+chr(39)))]
kept, blocked = lp.prepare(rows, {})
print(\"в очереди:\", len(rows), \"| промоут возьмёт:\", len(kept), \"| заблокирует:\", len(blocked))
print(collections.Counter(r for _x, r in blocked).most_common())
for r in kept: print(\"  ВОЗЬМЁТ  \", r[\"source_file\"], \"|\", r[\"raw_name\"], \"=\", r[\"value\"], \"→\", r[\"_cname\"])
for r, why in blocked: print(f\"  [{why}]\", r[\"source_file\"], \"|\", r[\"raw_name\"], \"=\", r[\"value\"])
"'
```

Разложи вывод на четыре группы — они требуют РАЗНОГО:

| группа | признак | что с ней делать | решение владельца? |
|---|---|---|---|
| 1 | промоут ВОЗЬМЁТ | запустить промоут | нет |
| 2 | `unmapped-nonanalyte`, `value=None` | отклонить: у канона нет формы для качественного результата | нет |
| 3 | `unmapped-nonanalyte`, значение ЕСТЬ | свести имя к канону ИЛИ отклонить | **ДА** |
| 4 | `page-role:narrative` | отклонить по правилу «страница-комментарий не импортируется» | нет |

## Шаг 2. Проверить группу 1 глазами ПЕРЕД промоутом

Промоут возьмёт строку, если её имя сводится к известному канону. Сведение
бывает НЕВЕРНЫМ, и тогда промоут добавит измерение не в тот тренд.

Проверяй материал вместе с именем. Возможный сбой: похожие названия результатов
из разных материалов сводятся к одному каноническому имени. Даже без значения
такая строка указывает на небезопасное сведение.

Смотри на колонку `→ _cname` в выводе шага 1. Всё, что выглядит подозрительно
(материал в имени не совпадает с целью, «кал»/«моча»/«слюна» → кровяной аналит),
уходит в reject шага 3, а не в промоут.

## Шаг 3. Составить reject-файл

Формат — тот же, что экспортирует HTML-лист ревью (`lab_review_sheet.py`); путь и
значение ниже условные:

```json
[
  {"source_file": "<папка>/panel_example.pdf", "canonical": "Группа крови", "value": null},
  {"source_file": "<папка>/panel_example.pdf", "canonical": "ПСА свободный*", "value": 1.23}
]
```

Ключ сверки в `lab_promote._apply_rejects`: `run_id` + `source_file` +
(`canonical_name` ИЛИ `raw_name`) + значение с точностью 1e-6. Для строк без
значения ставь `"value": null` — код сводит его к `-1e30` с обеих сторон и
матч проходит.

**Имя бери ДОСЛОВНО из вывода шага 1**, включая пунктуацию и регистр.
Выдуманный немедицинский пример: `DEMO-C` и `DEMO-С` выглядят похоже, но
заканчиваются латинской `C` и кириллической `С`. Внешне одинаковые имена
не обязаны совпадать побайтно.

Положи файл на Studio: `/tmp/rej_review.json`.

## Шаг 4. ⚠️ ЛОВУШКА: `--reject-file` пишет ДАЖЕ БЕЗ `--execute`

`_apply_rejects` вызывается в самом начале `plan()` и **делает `commit`** до
того, как код дойдёт до ветки dry-run (`lab_promote.py:446`). То есть:

```bash
# ЭТО УЖЕ ОТКЛОНИТ СТРОКИ, несмотря на отсутствие --execute
python3.11 lab_promote.py --run-id example-run --reject-file /tmp/rej_review.json
```

Порядок, который не кусается:

```bash
# 4.1 — сначала dry-run БЕЗ reject-файла: посмотреть, что промоут сделает вообще
ssh <studio_ssh> 'cd ~/health_scripts && \
  /opt/homebrew/bin/python3.11 lab_promote.py --run-id example-run' | head -60

# 4.2 — снапшот БД (§3), потому что дальше пойдёт запись
ssh <studio_ssh> 'cp -a ~/health/data/health.db \
  ~/health/data/health.db.pre_review_$(date +%Y%m%d_%H%M%S)'

# 4.3 — применить reject (запишет статусы) и посмотреть план ещё раз, УЖЕ без них
ssh <studio_ssh> 'cd ~/health_scripts && \
  /opt/homebrew/bin/python3.11 lab_promote.py --run-id example-run \
  --reject-file /tmp/rej_review.json' | head -60

# 4.4 — только теперь запись в канон
ssh <studio_ssh> 'cd ~/health_scripts && \
  /opt/homebrew/bin/python3.11 lab_promote.py --run-id example-run \
  --execute'
```

Читай в выводе 4.3 два гейта: **Гейт-2 ПОЛНОТА** (старое без покрытия — оно НЕ
удаляется) и **Гейт-2b ПРИТОК** (новые имена, которых в каноне не было никогда).
Приток с незнакомыми именами — повод остановиться, а не «наверное нормально».

## Шаг 5. Группа 3 — единственное, где нужен ты

Строка несёт настоящее число, но её имени канон не знает. Три исхода:

1. **Синоним существующего аналита** → добавить в `lab_canon._SYNONYMS`
   (`lab_canon.py`, начало файла) и прогнать `tests/unit/test_lab_canon.py`.
2. **Новый аналит** → новое каноническое имя там же + запись в `lab_refs`,
   если у него есть референсы.
3. **Не аналит** → reject шага 3.

Путь через `lab_name_aliases` (`confirmed=1`) существует и промоут его читает
первым (`lab_promote._canon`), но принимает ТОЛЬКО цель, которую канон уже
знает — иначе имя завело бы новый тренд мимо справочника. То есть алиас на
неизвестное имя не работает; сперва имя должно появиться в `lab_canon`.

```bash

```

## Известные ловушки

- **`--reject-file` пишет без `--execute`** (шаг 4).
- **Имя с гомоглифом** — латиница и кириллица в одном корпусе (шаг 3).
- **Неверная канонизация** уводит измерение в чужой тренд молча (шаг 2).
- **Промоут заменяет ТОЛЬКО покрытое** — старые (дата, аналит) без покрытия
  сохраняются как «старое непокрытое», а не удаляются. Это защита от потери,
  но она же прячет утечку: обе выглядят одинаково.
- **Не считай корзину `gold` пустой заранее.** Измерь её в текущем прогоне.
  Она отличается от `review`, и промоут также принимает её строки.

## Проверки при сверке очереди с каноном

### Считай переходы состояния, а не затронутые строки

`cur.rowcount` может учитывать строки, уже имевшие целевой статус. Сравни
снимки до и после по ключу строки и статусу; отличай повторный UPDATE от
нового отклонения. Фактические изменения фиксируй отдельно от SQL-счётчика.

### Дедупликация может оставить старый статус в очереди

Если `split_groups` выбирает представителя, обновление статуса только по факту
его вставки может оставить остальные строки в `review`. Проверь кандидатов:

```sql
SELECT id, run_id, page, review_status, value FROM lab_results_staging
WHERE source_file = ? AND raw_name = ? ORDER BY id;
```

Затем проверь наличие результата под каноническим именем, той же датой и источником:

```sql
-- Compare the canonical name, date, source and value.
SELECT COUNT(*) FROM lab_results
WHERE date = ? AND source = ? AND test_name = ?
  AND ABS(COALESCE(value, -1e30) - ?) < 1e-6;
```

Только совпадение допускает `review_status='promoted'`. Без совпадения строка
остаётся нерешённой. Алерт о статусе очереди сам по себе не доказывает, что
результата нет в каноне.

### Проверяй достижимость и смысл синонимов

Ключ словаря должен быть достижим через `_key`. Выдуманный немедицинский пример:
если `_key` удаляет скобки, буквальный ключ `demo (suffix)` в таком виде
недостижим. Прежде чем нормализовать ключи, проверь, не сольются ли разные
материалы или единицы в один тренд; не объединяй их механически.

У двуязычных имён проверь оба разделителя: `/` и `\`. Если единица меняет
смысл, одного синонима недостаточно: нужно явное правило размерности.
Наличие или отсутствие имён в конкретном корпусе не является общим правилом.

### Критерий завершения

Снова измерь остаток очереди и объясни каждую нерешённую причину. Сверь изменения
канона с запланированным набором в обе стороны: ничего не потеряно и ничего
неожиданного не добавлено. Отдельно от счётчиков очереди проверь вывод читателя.
Повторяющийся дрейф статусов исправляй в месте их записи промоутом; нерешённые
вопросы словаря и размерности фиксируй без утверждения, что они уже реализованы.
