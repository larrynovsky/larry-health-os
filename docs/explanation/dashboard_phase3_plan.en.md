## Scope (from the discussion on 2026-05-15)

**Inline field editing** (values change):
- `/profile` — `patient_profile.value_text` / `value_json`
- `/tasks` — `tasks.content`, `tasks.resolved_text`
- `/consultations` — `consultations.key_findings`, `consultations.specialist_name`
- `/events` — `periods.notes`, `periods.tags`

**Status actions** (records are not edited; only their state changes):
- `/hypotheses` — "accept" / "reject" buttons → changes `memory.active` + appends `payload.resolution_type`
- `/problems` — "stop monitoring" / "resume" → changes `problem_list.status`
- `/protocols` — "retire" → changes `protocols.status='retired'` + `retired_at`
- `/experiments` — "complete successfully" / "cancel" → changes `experiments.status` + `result`

Remain read-only: `/patterns` (historical log, not editable), `/labs` (external data), `/constitutions` (regenerated by a script).

## SQLite checks (performed 2026-05-15)

The database was inspected before implementation planning. The results below are now concrete facts, not assumptions.

**Current `health.db` configuration:**
- `journal_mode=wal` ✅ — the writer does not block readers (the dashboard's read-only connection will continue working during writes)
- `synchronous=1` (NORMAL) ✅ — optimal for WAL
- `busy_timeout=0` ❌ — on contention, SQLITE_BUSY is returned immediately

**What this means for Phase 3:**
Every write connection in `dashboard.py` must set `PRAGMA busy_timeout=5000` (5 seconds) immediately after `connect()`. This closes the bug class "`morning_report` writes → the user clicks confirm in the dashboard → 500 error." With the timeout, `dashboard.py` will wait up to 5 seconds and then acquire the lock.

**Audit log:**
There is no `audit_log` or `dashboard_edits` table. `agent_reports` (present in the database) is specialized: required fields are `agent_type`, `agent_name`, `data_queried`, `pubmed_ids`, `peers_reviewed`, `findings`, `recommendations`. Putting "dashboard edit field X" there violates its semantics (agent_type accepts `lifestyle|specialist|therapist|synthesizer`; the dashboard is not an agent).

Decision: **a new `dashboard_edits` table** — its own simple audit log.

**Schema observations (for Phase 3 endpoints):**

| Table | Columns for editing | Tracking |
|---|---|---|
| `patient_profile` | `value_text`, `value_json` | `updated_at`, `updated_by` — populate with `'dashboard'` |
| `memory` (hypothesis) | `value` (JSON string), `active` | `updated_at` exists. For confirm/reject, parse `value` → mutate `payload.resolution_type` → serialize with `json.dumps(ensure_ascii=False)` |
| `protocols` | `status`, `retired_at` | Tracking through `dashboard_edits` |
| `tasks` | `content`, `status`, `resolved_at`, `resolved_text`, `resolution_type` | resolution_type for done = `'completed_via_dashboard'` |
| `problem_list` | `status`, `last_updated` | `last_updated` is already NOT NULL — update it |
| `experiments` | `status`, `result`, `end_date` | Tracking through `dashboard_edits` |
| `consultations` | `key_findings`, `specialist_name` | ❌ No `updated_at` — audit only through `dashboard_edits` |
| `periods` | `notes`, `tags` | ❌ No `updated_at` — audit only through `dashboard_edits` |

## Architectural contract

### Stack

- **HTMX** for inline editing and POST actions. Not jQuery, Alpine, or React. HTMX is "server-side rendering with small interactions": declarative `hx-post` attributes in HTML, the server returns an HTML fragment, and HTMX replaces the block.
- **No modals**. The "accept" button immediately sends a POST and replaces the card with a closed one. Inline editing: click a value → input → blur → POST → value updated.
- **We do not use CSRF.** Trust boundary = the Tailscale network. POST endpoints are not exposed outside Tailscale; a CSRF token adds no protection (an attacker inside the mesh already has terminal access). This is a design choice, not an oversight.
- **Separate read and write connections.** Currently, `_q()` uses a read-only URI. For writes, a separate function `_w(sql, params)` with a regular connection + `PRAGMA busy_timeout=5000`.

### Concurrent writes

WAL is enabled → writers do not block readers. The dashboard reads (for `_q()`) and writes (for `_w()`) to the same database in parallel with `morning_report`, `gp_agent`, `consilium`, and others. `busy_timeout=5000` allows 5 seconds to wait for a lock. This covers 99% of contention for a single-user system.

If SQLITE_BUSY still occurs after 5 seconds, the endpoint returns 503 + HTMX reverts the UI with an error chip: "Database busy, try again." This is better than silent failure.

### Endpoint contract

`POST /api/<entity>/<id>/<action>` or `PATCH /api/<entity>/<id>` for inline field editing.

Returns: an HTML fragment with the updated card / row. HTMX replaces the block with `id="entity-{id}"`.

All endpoints log the write in **`dashboard_edits`** (the new table from 3A.2) — an audit trail of who edited what and when.

## Implementation stages

### 3A: Foundation (HTMX + write infrastructure + migration) (~1 hour)

#### 3A.1 Self-hosted HTMX

1. `wget https://unpkg.com/htmx.org@1.9.10/dist/htmx.min.js -O ~/health_scripts/dashboard_static/htmx.min.js`
2. `base.html`: `<script src="/static/htmx.min.js?v={{ js_version }}"></script>`
3. `templates.env.globals["js_version"] = int(mtime(htmx.min.js))` next to `css_version`
4. Smoke: `<button hx-post="/api/ping" hx-swap="outerHTML">ping</button>` → the endpoint returns `<span>pong</span>`

#### 3A.2 Write infrastructure

```python
def _w(sql, params=()):
    """Write connection — busy_timeout=5000, proper closing."""
    c = sqlite3.connect(str(DB_PATH))
    c.execute("PRAGMA busy_timeout=5000")
    try:
        cur = c.execute(sql, params)
        c.commit()
        return cur.lastrowid
    finally:
        c.close()
```

Use in every POST endpoint. Never open a connection with `mode=ro` for writes.

#### 3A.3 `dashboard_edits` migration

```sql
CREATE TABLE IF NOT EXISTS dashboard_edits (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    ts            TEXT DEFAULT (datetime('now')),
    entity        TEXT NOT NULL,    -- patient_profile|memory|protocols|tasks|...
    entity_id     TEXT NOT NULL,    -- INTEGER as TEXT (profile uses key)
    action        TEXT NOT NULL,    -- edit_field|confirm|reject|retire|...
    field         TEXT,             -- which field was changed (for inline-edit)
    old_value     TEXT,             -- what it was
    new_value     TEXT,             -- what it became
    actor         TEXT DEFAULT 'dashboard'
);
CREATE INDEX idx_dashboard_edits_entity ON dashboard_edits(entity, entity_id);
CREATE INDEX idx_dashboard_edits_ts     ON dashboard_edits(ts);
```

Helper:
```python
def _log_edit(entity, entity_id, action, field=None, old=None, new=None):
    _w("""INSERT INTO dashboard_edits(entity, entity_id, action, field, old_value, new_value)
          VALUES (?, ?, ?, ?, ?, ?)""",
       (entity, str(entity_id), action, field, old, new))
```

Run once from the migration script `scripts/migrations/2026-05-15_dashboard_edits.py`; idempotent through `IF NOT EXISTS`.

**Self-host vs CDN risk:** self-hosting was chosen to keep Tailscale-only clean (no external fetches for core functionality). Google Fonts remain an exception — the patient has not withdrawn consent to Google.

### 3B: Profile inline editing (~2–3 hours)

#### 3B.1 Template with two `.kv-value` modes

```html
<td class="kv-value"
    hx-get="/api/profile/{{ r.key }}/edit"
    hx-trigger="click"
    hx-swap="outerHTML">
  {{ r.value_text or r.value_json }}
</td>
```

On click, it is replaced with `<td><input ... hx-post="/api/profile/{key}" hx-trigger="blur"></td>`. After blur, the server returns `<td class="kv-value">новое значение</td>` again.

#### 3B.2 Endpoints

```python
import html as _html

@app.get("/api/profile/{key}/edit", response_class=HTMLResponse)
def profile_edit_field(key: str):
    rows = _q("SELECT value_text FROM patient_profile WHERE key=?", (key,))
    if not rows: raise HTTPException(404)
    current = rows[0]["value_text"] or ""
    return (f'<td class="kv-value kv-value--editing">'
            f'<input name="value" value="{_html.escape(current)}" '
            f'hx-post="/api/profile/{key}" hx-trigger="blur,keyup[key==&quot;Enter&quot;]" '
            f'hx-swap="outerHTML" autofocus></td>')

@app.post("/api/profile/{key}", response_class=HTMLResponse)
def profile_save_field(key: str, value: str = Form(...)):
    old_rows = _q("SELECT value_text FROM patient_profile WHERE key=?", (key,))
    old = old_rows[0]["value_text"] if old_rows else None
    _w("""UPDATE patient_profile
          SET value_text=?, updated_at=datetime('now'), updated_by='dashboard'
          WHERE key=?""", (value, key))
    _log_edit("patient_profile", key, "edit_field", field="value_text", old=old, new=value)
    return (f'<td class="kv-value" '
            f'hx-get="/api/profile/{key}/edit" hx-trigger="click" hx-swap="outerHTML">'
            f'{_html.escape(value)}</td>')
```

#### 3B.3 Edge cases

- **`value_json` (structured JSON)**: use a `<textarea>` instead of an `<input>` for these. Validation uses `json.loads()` on the server; if parsing fails → 422 + red error text.
- **Empty value**: allowed, UPDATE with NULL.
- **Escaping**: always through Jinja `{{ }}` or Python `html.escape()`.

#### 3B.4 Audit log

`profile_save_field` already calls `_log_edit("patient_profile", key, "edit_field", field, old, new)` — this writes to `dashboard_edits`. No separate steps are needed.

### 3C: Status actions for hypotheses (~1.5 hours)

#### 3C.1 Buttons on the card

```html
<article class="card card--warning" id="hyp-{{ h.id }}">
  ...
  <footer class="card-foot">
    <button class="action-pill"
            hx-post="/api/hypotheses/{{ h.id }}/confirm"
            hx-target="#hyp-{{ h.id }}"
            hx-swap="outerHTML">принять</button>
    <button class="action-pill action-pill--ghost"
            hx-post="/api/hypotheses/{{ h.id }}/reject"
            hx-target="#hyp-{{ h.id }}"
            hx-swap="outerHTML">отвергнуть</button>
  </footer>
</article>
```

CSS addition: `.action-pill--ghost { background: transparent; color: var(--color-text-hint); border: 0.5px solid var(--color-border-soft); }`

#### 3C.2 Endpoints

```python
@app.post("/api/hypotheses/{id}/{action}", response_class=HTMLResponse)
def hyp_action(request: Request, id: int, action: str):
    if action not in ("confirm", "reject"):
        raise HTTPException(400)
    
    # Find the record
    row = _q("SELECT value FROM memory WHERE id=?", (id,))[0]
    payload = json.loads(row["value"]) if row["value"] else {}
    payload["resolution_type"] = "confirmed" if action == "confirm" else "rejected"
    payload["resolved_by"] = "dashboard"
    payload["resolved_at"] = datetime.now().isoformat()
    
    _w("""UPDATE memory SET active=0, value=?, updated_at=datetime('now')
          WHERE id=?""",
       (json.dumps(payload, ensure_ascii=False), id))
    _log_edit("memory", id, action, field="payload.resolution_type",
              old=row.get("value"), new=payload["resolution_type"])
    
    # Return the closed version of the card
    return templates.TemplateResponse(request, "_hypothesis_card.html", {
        "h": {**row, "payload": payload, "active": False},
    })
```

This requires the partial `_hypothesis_card.html` — one card without wrappers. `hypotheses.html` includes it in a loop.

#### 3C.3 Resolution_type semantics

CBCR methodology discussion (see RTFM):
- `confirmed` — the hypothesis was confirmed by data
- `rejected` — the data refuted it
- `needs_specialist` — requires a consultation (already in the payload)
- `superseded` — replaced by a more precise hypothesis

So the buttons are only `confirm` / `reject`. `needs_specialist` is set automatically by the CBCR pipeline.

### 3D: Status actions for protocols/problems/experiments (~1.5 hours)

The same pattern as 3C, but with different actions:

| Entity | Actions | SQL |
|---|---|---|
| `protocols` | `retire` | `UPDATE protocols SET status='retired', retired_at=datetime('now') WHERE id=?` |
| `problems` | `archive` (active/monitoring → resolved) / `reopen` (resolved → active) | `UPDATE problem_list SET status=?, last_updated=datetime('now') WHERE id=?` |
| `experiments` | `complete` / `cancel` | `UPDATE experiments SET status=?, result=?, end_date=date('now') WHERE id=?` |

⚠️ **Before starting 3D**: check which `status` values currently exist in `problem_list`: `SELECT DISTINCT status FROM problem_list`. Possible candidates: `active`, `monitoring`, `resolved`, `watch`. Decide which transitions are valid (does "stop monitoring" in the UI mean `monitoring→resolved` or `active→resolved`? both?). From real data, not memory.

Partials: `_protocol_card.html`, `_problem_card.html`, `_experiment_card.html`. Each action calls `_log_edit(entity, id, action, ...)`.

### 3E: Tasks editing (~1 hour)

Tasks are special: `content` is editable, and there are status actions (`done` / `snooze`).

Inline editing of `content` works like the profile, but through a `<textarea>` for long texts.

Status actions:
- `done` → `UPDATE tasks SET status='completed', resolved_at=datetime('now'), resolution_type='completed_via_dashboard', resolved_text=? WHERE id=?` (resolved_text may be an empty string for a simple "done," or contain an answer if available)
- `snooze` → `UPDATE tasks SET status='snoozed' WHERE id=?` + optionally `deadline` through a mini-form

### 3F: Consultations / Events (~1 hour)

The same inline editing for `key_findings` / `specialist_name` (consultations) and `notes` / `tags` (periods). No status actions.

⚠️ Both tables (`consultations`, `periods`) **lack `updated_at`** — the only audit will be in `dashboard_edits`. This is an explicit trade-off: no schema migration (more expensive); rely on dashboard_edits. If a global `last_modified` is ever needed, add it in a separate migration.

`periods.tags` is stored as a JSON string (`'["oncology","exampla"]'`). Inline editing through an `<input>` — the user sees raw JSON. This is not the best UX, but it is honest. Alternatives (a tag-picker UI) — defer until Phase 4.

### 3G: Audit & rollback (~0.5 hours)

Audit is already implemented in 3A.3 (the `dashboard_edits` migration) and called automatically from every endpoint through `_log_edit(...)`. At this stage, add the `/audit` page to view the timeline:

```python
@app.get("/audit", response_class=HTMLResponse)
def audit(request: Request):
    rows = _q("""SELECT ts, entity, entity_id, action, field, old_value, new_value
                 FROM dashboard_edits ORDER BY ts DESC LIMIT 200""")
    ...
```

Template: a `.dense` table with an entity filter through a query parameter. We **do not implement** UI-level rollback (it would let the user shoot themselves in the foot) — if an edit goes to the wrong place, read `dashboard_edits` and roll it back manually.

### 3H: Tests (~1–2 hours)

Minimum:
1. **Endpoint smoke**: each POST endpoint returns 200 for valid input and 4XX for invalid input
2. **DB invariant**: after a hypothesis is `confirm`ed, `active=0` AND `payload.resolution_type='confirmed'`
3. **HTMX integration**: one Playwright test (or curl-based mock) that the card is actually replaced after a click

Add tests to `tests/integration/test_dashboard_actions.py`.

## Risks and uncertainties

| Risk | Probability | Mitigation |
|---|---|---|
| HTMX cache in Safari (old JS) | medium | Cache-bust JS through mtime, like CSS |
| Write conflict with `morning_report` | low | SQLite WAL, retry through busy_timeout |
| `value_json` validation does not cover all edge cases | medium | Server-side `json.loads()`; on error, 422 + red highlighting |
| Inline-edit textarea does not work on long constitutions | high | Constitutions are read-only — correctly so (regenerated by a script) |
| User accidentally "accepts" a hypothesis with a click | medium | HTMX confirmation dialog (`hx-confirm="Точно принять?"`) for status actions |
| Memory `category='hypothesis'` has old hypotheses without a payload | high | Endpoint must parse gracefully — still works if payload=`{}` |

## User decisions (2026-05-15)

Resolved before Phase 3 starts:

1. **After confirm/reject, the card moves to the archive.** It immediately disappears from the main list and appears in the "archive" section below. Implemented through `active=0` (for memory) or `status='resolved'/'retired'/'cancelled'/'completed'` (for the others).
2. **Confirmation dialog: browser `confirm()`** through `hx-confirm="Точно?"`. Ugly, but it works. Each status button receives this attribute.
3. **`confidence` does NOT change** after confirm/reject. Only `payload.resolution_type` + `active=0`.
4. **Actual `problem_list.status` values:** `resolved` (archive), `active_monitoring` and `watchful_waiting` (active). Transitions: archive → `resolved`. Reopen → `active_monitoring` (closer monitoring).
5. **No HTMX SRI hash.** Self-hosting on the same machine — SRI does not protect against internal substitution.

## What we do not do in Phase 3

- Create new records (edit existing only). Hypotheses / tasks are created through the Telegram bot or external scripts.
- Delete records. Only soft-delete through `active=0` or `status='archived'`.
- Bulk operations. One click = one record.
- Undo (except server-side git revert for extreme cases).
- Auth/CSRF/rate limiting. Trust boundary = Tailscale.
