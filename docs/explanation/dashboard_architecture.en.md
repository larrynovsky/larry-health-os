# Dashboard — Explanation

Why these decisions were made. Reference (what exists) — `docs/reference/dashboard.md`. Changes — `docs/how-to/extend_dashboard.md`.

## Why a dashboard

Context: before 2026-05-15, "live facts" about the patient lived in three places:
- The database (10+ tables: `patient_profile`, `protocols`, `periods`, `hypotheses`)
- Markdown constitutions (5 files, regenerated by a script)
- The Telegram bot (read-only responses, no overview)

Audit #179 (AUDIT-DATA-LIFECYCLE) found three classes of "graveyards": `patterns`/`context_events`/`recommendations` accumulate but are never closed out. A graveyard = a fact the patient cannot see in an overview.

The dashboard fulfills one contract: **a visual place that shows everything there is, without having to ask the Telegram bot or read Markdown in an editor**. Read-first, edit-second.

## Why Tailscale-only

Trust boundary = the private Tailscale mesh network (2 devices: MacBook + Studio).
Alternatives considered:
- **Cloudflare Tunnel / public Tailscale Funnel** — exposes the dashboard to the internet. Requires an auth layer (OAuth, basic auth, etc.). A large attack surface for patient PII (genes, diagnoses, psychology).
- **Local (`127.0.0.1`)** — Studio runs headless; MacBook cannot see its localhost.
- **Tailscale interface** — a compromise: mesh-only access, without an auth layer (trust = access to the mesh); the patient sees the dashboard from any device on their network.

Decision: `uvicorn.run(app, host="<studio_host>", port=8001)`. The host is explicitly a Tailscale IP, not `0.0.0.0` — this prevents the dashboard from accidentally listening on other interfaces (for example, if Studio ever joins an unfamiliar network).

## Why FastAPI + Jinja2, not Flask

The initial thought was "I'll use Flask" — this is mentioned in `dashboard-design/README.md`. In practice, FastAPI proved more convenient for three reasons:
1. **Starlette `TemplateResponse(request, name, ctx)`** — the new API is simpler than `flask.render_template` because it passes `request` automatically (needed for `request.url.path` in the sidebar)
2. **Async-ready** — if streaming long responses is needed later (large constitutions, history queries), the transition is painless.
3. **One process with other FastAPI microservices** in Health OS (if a Telegram webhook using FastAPI ever appears — a unified stack).

Trade-off: the design document mentions Flask; the implementation uses FastAPI. The component contract is identical (Jinja2 + class-based CSS), so the mix is acceptable.

## Why server-side rendering, not an SPA

The repo had `static/index.html` — a 51KB React SPA from the VPS era. Disabled because:
- The build step (React+Webpack) complicates deployment
- State sync (frontend ↔ backend) breaks every other time
- Security requires API endpoints, CSRF, JWT, and that whole "enterprise" layer

A dashboard for **one user** does not need SPA complexity. Jinja2 renders HTML in one pass; there is no client state and no XHR. This is **simplicity** you can feel when reading the code.

HTMX will arrive in Phase 3 — still "server-side rendering with small interactions," not an SPA.

## Why Toscana rather than a "normal dashboard"

The patient's contract: "**this is not a dashboard, it is a journal**."

A dashboard implies:
- A high density of numbers
- Bar charts / heatmaps
- Bold-bombing for "highlight-and-scan"
- Cool colors (blue, gray, a light background)

A journal implies:
- Serif typography for extended reading
- Warm colors (terracotta, cream)
- Space between thoughts
- Italic section labels ("currently under observation") instead of CAPS LETTERS
- Inset shadows, not elevation — a cozy feel, not a poster

The design system is formalized in `~/health/dashboard-design/` (outside the repo because it is owned by the patient). Contract:
- **Tokens only** in templates. No `#XXXXXX`, no `14px`. If a needed token is missing, add it to `tokens.css`.
- **Serifs for meaning, sans for UI, mono for values**. This is semantic markup through type.
- **`№` instead of `#`** for IDs — a literary register, not GitHub.
- **lowercase italic for section captions** — "hypotheses," not "HYPOTHESES" or "**Hypotheses**."

## Antipattern: bold-bombing

Discovered while critiquing `/constitutions/sleep` on 2026-05-15. Markdown emits `<strong>` for every list lead, and with insufficient vertical spacing the eye stops responding to the bold anchor — it becomes a noisy grid. Solution:
- Space between `<li>` elements: 4px → 14px
- Space before h2: 24px → 44px
- Narrow line measure: `max-width: 65ch` (through the `.narrative` class)

Lesson: bold needs **space around it**, otherwise it becomes a continuous pattern instead of emphasis.

## Cache busting through mtime

Problem: a CSS edit on the server does not appear in the browser because Safari caches `dashboard.css` forever.

Solution: `templates.env.globals["css_version"] = int(mtime(dashboard.css))`. `<link href="dashboard.css?v={{ css_version }}">` changes with every CSS edit.

Trade-off: for the new `css_version` to reach the HTML, FastAPI must **reread** mtime when loading `dashboard.py`. So a CSS edit requires a dashboard `launchctl reload`, or `templates.env.globals["css_version"]` must be computed **on every request** (more expensive). The first approach is currently selected — reload-on-deploy, because deployments require a reload anyway.

## Deployment flow

Single canonical Studio (after the 2026-05-09 migration, docs/explanation/git_architecture.md):
1. Edit files locally (MacBook → outputs) or over ssh
2. `scp` to Studio (`~/health_scripts/dashboard_static/` or `dashboard_templates/`)
3. If you edited `.py`, run `launchctl unload && load` for the dashboard
4. If you edited only CSS/HTML, the browser picks it up through cache busting + Jinja template auto-reload
5. `curl http://<studio_host>:8001/...` for a smoke check
6. `git commit` on Studio immediately (CLAUDE.md rule #1)

All `.py` changes made through ssh-edit require an immediate commit, or they will disappear at the next `git pull` / `reset` (CLAUDE.md rule #1, incident of 2026-05-10).

## Current compromises and known issues

| What | Why it is this way now | What would be better |
|---|---|---|
| Google Fonts through CDN | Cheapest start | Self-host fonts in `dashboard_static/fonts/` — fulfills "dashboard works offline" |
| Mobile = inline-block sidebar | Tabbar requires a FAB + a four-item selection decision | Tabbar from design §11 — a separate task |
| `today_meta = «<дата>»` | Treatment anchor dates (regimen end, device start) are not used | Query `periods` for active treatments + a relative date |
| Cache busting requires reload | CSS mtime is read once at boot | `globals` through a callable — more expensive, but live |
| Read-only | As designed for Phase 1+2 | Phase 3 on the roadmap |
| Drop cap through `::first-letter` | Minimal markup, works on raw Markdown | May fail if the first element is an h1/table |

## What was not done

- The dashboard does not try to replace the Telegram bot. The bot remains for "push" (morning briefing, alerts); the dashboard is for "pull" (when the patient wants to look)
- The dashboard does not try to make essays written by others accessible — it is an interface for one user who knows the context
- The dashboard does not perform analytics (no charts, no aggregations) — `longitudinal_analysis.py` and the morning brief exist for that
