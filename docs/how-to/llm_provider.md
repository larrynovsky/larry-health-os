# Как поставить систему с ключом другого поставщика моделей

Урок [первой установки](../tutorials/first_install.md) ставит систему с ключом Anthropic — на нём
проверено всё. Этот рецепт — для тех, у кого есть ключ OpenAI или Gemini и нет ключа Anthropic.

## Сначала посмотрите, что будет работать

Работает только та часть системы, чья модель прошла проверку у этого поставщика: таблица —
[что работает на каком поставщике](../reference/llm_providers.md). Функция, чья модель проверку
не прошла, отказывает словами, а не отвечает непроверенной моделью. Проверка узкая: чтение
бланков анализов, разбор лечения из текста и короткие текстовые задания. Насколько хорошо модель
другого поставщика пишет утренний отчёт или рассуждает в консилиуме, с Claude не сравнивалось.

## Установка

Запустите `bash install.sh`, как в уроке. Новая установка спросит:

```
Каким ключом будете пользоваться? Анализы, выписки и переписка с ботом уходят выбранному поставщику.
  1 — Anthropic (рекомендуется: на нём проверено всё)
  2 — OpenAI
  3 — Gemini (Google)
Номер [1]:
```

Ответьте `2` или `3`. Скрипт спросит ключ этого поставщика (ввод скрыт), проверит его списком
моделей (это бесплатно) и положит в `secrets/openai_key` или `secrets/gemini_key`. Ключ OpenAI
берут на platform.openai.com → API keys (и пополняют баланс), ключ Gemini — на aistudio.google.com →
Get API key. В конце скрипт напишет, что все функции прошли проверку, или перечислит словами, что не работает.

Без вопросов (например, на сервере) поставщик называют флагом:

```bash
LLM_KEY=… HEALTH_TZ=Europe/Berlin TELEGRAM_TOKEN=… TELEGRAM_CHAT_ID=… \
  bash install.sh --provider gemini --non-interactive
```

DeepSeek сейчас не предлагается: на нём не работают анализы с фото и консилиум.

## Сменить поставщика позже

Повторный `bash install.sh` — это обновление: он поставщика не спрашивает и выбор не меняет.
Чтобы сменить поставщика, запустите его с флагом, например `bash install.sh --provider openai`:
строка `HEALTH_LLM_PROVIDER` в `.env` поменяется, контейнеры пересоздадутся, база и ключи останутся.

## Что важно знать

- Все тексты и документы, которые система отправляет модели (анализы, выписки, чат), уходят
  выбранному поставщику. Его условия обработки данных — ваше решение.
- Счёт за модели — на вашем ключе у поставщика. Баланс скриптом не проверить: пополните его.
- Список допущенных моделей приходит вместе с версией системы. Новые проверки и замена модели,
  которую поставщик отключил, появятся у вас после обновления: о новой версии напишет бот,
  обновление — повторный `bash install.sh`.
- Как система выбирает модель и что происходит, когда поставщик её отключает, —
  [объяснение](../explanation/model_choice.md).

## Если поставщик не указан: переходный выпуск

Непустой `HEALTH_LLM_PROVIDER` имеет приоритет. Без него при наличии
`anthropic_key` этот переходный выпуск сохраняет Anthropic, даже если рядом
есть другие ключи, и пишет предупреждение с просьбой задать переменную.
Иначе выбирается единственный файл ключа из `methodology/llm_providers.json`.
Ноль или несколько не-Anthropic ключей, либо неверное явное значение блокируют
вызовы ИИ: причина — в логе, инструкция — в боте при старте (ru/en).
Успешно отправленная инструкция не повторяется до исправления конфигурации;
неудачная отправка повторяется при следующем старте.

Старое `HEALTH_LLM_PROVIDER=anthropic` невозможно отличить от выбора человека.
Для другого поставщика исправь `.env`, например `HEALTH_LLM_PROVIDER=openai`,
затем выполни `docker compose up -d`. Публичный шаблон без выбора оставляет
значение пустым; владельческий override передаёт всем службам явный выбор,
а при пустом значении — Anthropic. Непустая `.env` или окружение compose старше этого резерва.

## Native/tenant и безопасный порядок обновления

Общее окружение всех native-шаблонов задаёт `native_environment` в
`templates/launchd/placement.yaml`. `render_launchd` применяет его ко всем
шаблонам, включая host/env/none; `render_tenant` — ко всем ready-службам из
`tenant_services.yaml`. Настройка `--provider openai` у `install.py` (также с
`--tenant`) переопределяет native Anthropic. Переменная окружения установщика
`HEALTH_LLM_PROVIDER` используется, если флаг не указан.

LLM-ключ нативного партнёра остаётся общим: `Path.home()/.health_secrets`,
а не `HEALTH_SECRETS_DIR`. При одной macOS-учётке владелец и партнёр читают
один каталог. `provider()` и `api_key()` используют один `_KEY_FILE.parent`.
Менять каталог ключа вместе с миграцией провайдера нельзя: это отдельное
изменение границы доступа и оплаты.

Порядок перехода (проверен по коду 2026-11-08):

1. Выпустить **совместимый** resolver с предупреждением и новые рендеры.
   Он сохраняет работу старых native-процессов с `anthropic_key` и другими ключами.
2. Compose владельца перерендеривается при deploy: `deploy_container.sh`
   вызывает `install.py --docker`, `--owner-override`, затем `compose up -d`.
   В override все службы получают явное значение, включая MCP, bug-inbox и sidecar.
3. **Native plist нужно мигрировать отдельно.** `install.py --launchd` и
   `--tenant` только пишут в `build/launchd`; deploy hooks не копируют их в
   `~/Library/LaunchAgents`, а `kickstart` не перечитывает изменённый plist.
   Сохрани резервные копии и список загруженных служб. Для существующих plist
   добавь `EnvironmentVariables.HEALTH_LLM_PROVIDER=anthropic`, сохранив их
   индивидуальные аргументы, расписание и пути. Новые рендеры — эталон настройки,
   не основание бездумно заменить все локальные plist.
4. Перезагрузи **только ранее загруженные** службы через bootout/bootstrap и
   проверь их окружение через `launchctl print gui/<uid>/<label>`; наличие
   строки в файле не доказывает её наличие у процесса. Не загружай отключённые
   службы владельца, перенесённые в контейнер: иначе появятся вторые писатели.
   Не запускай полный `--apply` на замороженной native-базе только ради plist:
   этот режим вызывает `init_db`. Рендеры можно вызвать отдельно без установки.
5. Лишь после проверки всех установленных **и загруженных** носителей (включая
   процессы партнёра) выпускать строгий отказ при нескольких ключах. В этом
   выпуске автоматического дедлайна или включения строгости нет.

Оракулы: `test_all_rendered_services_have_explicit_provider` проверяет полный
рендер owner/tenant, compose и optional-служб; исполняемый shell-тест проверяет,
что cron не перетирает выбранный в контейнере OpenAI на native Anthropic.
Проверки рендера не доказывают миграцию уже установленных LaunchAgents.
