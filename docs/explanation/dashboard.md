# Дашборд: витрина из БД за периметром tailnet: как это устроено и почему так

## Что изменилось

- **Добавлен инвариант `lan_ingest_write_only` (статус: holds):** зафиксировано, что процесс приёма данных по домашней сети работает только на запись и не показывает никаких страниц — браузерные запросы он отвергает. Это граница, в пределах которой утверждение доказано, не шире.

**Обновлено:** 2026-10-02


## Зачем он есть

У системы есть одно место, где всё хранится, — база данных с историей здоровья. Но смотреть на сырую базу неудобно и небезопасно: что-то можно случайно сломать, данные из разных мест начнут расходиться, и непонятно, чему верить.

Дашборд решает ровно одну задачу: дать удобный способ *видеть* то, что уже есть в базе, — и изредка поправить отдельную запись прямо здесь, не выходя куда-то ещё. Он не пытается стать вторым источником правды. Он — окно в единственный источник, который уже существует.

## Что он делает, простыми словами

**Читает из одной базы, пишет в ту же базу.** Никакой отдельной копии состояния дашборд не держит. Когда вы открываете страницу — он идёт в базу, берёт оттуда и показывает. Когда вы что-то правите — он пишет туда же, через тот же общий слой. Это принципиально: если бы у дашборда была своя копия, рано или поздно она разошлась бы с оригиналом, и стало бы непонятно, какой из двух вариантов правильный.

**Главная страница вычисляет, а не вспоминает.** Раздел «С чего начать» каждый раз при открытии смотрит в базу и ключи и заново вычисляет, в каком состоянии находится каждая возможность системы. Он не хранит флажок «этот раздел настроен». Если данные перестали поступать — страница это увидит сама, потому что источник «молчит». Если данных ещё не хватает — страница скажет об этом, потому что смотрит на то, что реально есть.

**Не запускается в режиме записи там, где не должен.** Система рассчитана так, что настоящая, «главная» копия базы живёт на одном устройстве. Если дашборд окажется запущен где-то ещё и начнёт писать — данные разойдутся через синхронизацию, и получится путаница, из которой сложно выбраться. Поэтому дашборд устроен так: если он не там, где должен быть, — он сразу останавливается при запуске, не дожидаясь, пока что-то пойдёт не так.

**Доступен только внутри частной сети.** Дашборд не торчит в открытый интернет. Он слушает только внутри закрытой сети (tailnet) — что-то вроде персонального впн для своих устройств. Публичного адреса у него нет. Это и есть граница периметра: не пароль на странице, а сама сеть.

**Есть отдельный процесс для приёма данных с телефона.** Когда телефон отправляет данные по домашней сети — это идёт не через дашборд, а через отдельный процесс на отдельном порту. Он принимает только данные и не показывает никаких страниц. Браузерные запросы он отвергает. Это разделение намеренное: инструмент для чтения и инструмент для записи живут отдельно и не мешают друг другу.

**Ревью анализов — особый случай.** Есть один санкционированный путь, где дашборд работает немного иначе: ревьюер читает данные из временного промежуточного хранилища и, одобрив, переносит их в основную базу. Это осознанная договорённость, а не случайное исключение из правил.

## Что честно сказать про его пределы

**У дашборда нет аутентификации — и это незавершённость, которую важно понимать.** Периметром служит сама закрытая сеть: дашборд слушает только на адресе внутри tailnet, без публичного доступа. Для семейного использования это осознанное решение. Но для медицинских данных это допущение, не гарантия. Это значит буквально: кто оказался внутри этой сети — тот видит всё, без дополнительной проверки личности. Этот вопрос остаётся открытым. Не стоит воспринимать периметр сети как полноценную защиту медицинских данных.

**Приём данных по домашней сети идёт без шифрования.** Внутри домашней Wi-Fi данные с телефона передаются открыто. И если телефон попытается отправить данные с тем же адресом вне дома — это тоже будет без шифрования. Это названо явно, как принятый риск, а не как незамеченная дыра.

## Где это в системе

Основная логика дашборда живёт в `dashboard.py`. Намерение подсистемы — что она делает и почему именно так — описано в `subsystem_intent.yaml`. Главная страница с вычисляемым состоянием возможностей опирается на `getting_started.board` и каталог `methodology/getting_started.yaml`, который должен покрывать каждую запись реестра возможностей — либо явно называть причину, почему та или иная возможность пропущена.

Дашборд — не центр системы и не её мозг. Он вторичен по замыслу: читает то, что уже есть, показывает это в удобном виде, и строго следит за тем, чтобы не стать источником путаницы там, где путаница недопустима.
