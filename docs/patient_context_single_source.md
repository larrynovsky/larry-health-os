# Единый контекст пациента (patient_context) — единственный источник

Статус: действует с 2026-07-05 (задача C). Enforced датчиком `tests/unit/test_patient_context_contract.py` (hard FAIL).

## Как добавить нового LLM-потребителя (how-to)

Если ты пишешь новый модуль/функцию, которая вызывает `client.messages.create` и **рассуждает о пациенте** (отчёт, консилиум, оценка гипотезы, подготовка разбора, чекин):

1. Собери промпт как обычно.
2. Вставь память из чата ОДНОЙ строкой:
   ```python
   import patient_context as pc
   block = pc.reasoning_block()   # факты из чата + свежие жалобы/поправки
   # ... добавь block в свой промпт секцией "ЗАМЕТКИ ИЗ ДИАЛОГОВ" ...
   ```
   `reasoning_block()` безопасен (внутри ловит ошибки, возвращает `""`) — обёртка `try/except` не нужна (и её завернёт silent-except guard).
3. Прогони `pytest tests/unit/test_patient_context_contract.py`. Если модуль — **извлечение/аналитика** (не рассуждает о состоянии пациента, напр. парсер лабов), добавь его `stem` в `ALLOWLIST` в тесте **с причиной в комментарии**, а не тяни контекст зря.

Не сделаешь ни то, ни другое — датчик уронит весь суит с именем твоего модуля/функции. Это by design: дрейф «новый потребитель забыл про память» становится структурно невозможным.

## API единого источника (reference)

Всё в `patient_context.py`:

| Функция | Что отдаёт | Кому |
|---|---|---|
| `build_patient_brief()` | полный профиль: идентичность + диагноз/лечение + анализы + факты из чата + вопросы + рекомендации | консилиум, wellally, lifestyle-агенты, системный промпт бота (через hai_core) |
| `reasoning_block()` | компактно: консолидированные факты из чата + свежие заметки/жалобы | конституции, gp weekly/monthly, оценка гипотез, consult_prep, чекин |
| `recent_notes(days=2)` | только свежие states/поправки о качестве данных | дневной отчёт (кольцо-ошибки и т.п.) |
| `chat_facts()` | только консолидированные факты (образ жизни) | внутренний для reasoning_block |

Все читают одни источники (`memory_facts`, профиль). `subject='self'` везде (R11 — чужие факты не попадают). Пересборка по требованию, без кэша (один процесс, малый масштаб → когерентность-протокол не нужен; всегда свежо).

## Почему единый источник (explanation)

Если каждый потребитель собирает профиль и подключает память самостоятельно, часть потребителей может пропустить поправку пользователя. Например, сообщение об ошибке датчика должно учитываться и в чате, и в последующем отчёте. Единый обязательный источник делает это требование общим.

Решение из software-архитектуры (не ML-фронтир): **single source of truth** + **fitness function**. Один модуль собирает контекст; контракт-тест обязывает каждого рассуждателя идти через него. Цитата, описывающая нашу боль: *«если правило живёт только в документации — это кандидат на fitness function; разрыв между написанным и проверяемым — там и гниёт»*. Мы перевели «читай память» из соглашения в проверку.

Датчик — способ 2 (точность до функции) для многофункциональных модулей (`gp_agent`: дневной/недельный/месячный — ловит «дневной читает, недельный слеп») + файловый backstop для новых модулей.
