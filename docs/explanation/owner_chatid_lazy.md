# Ленивый резолв владельца: почему бот узнаёт chat_id не при импорте

> **Тип документа:** Explanation (Diátaxis) — зачем так устроено и какие развилки были.
> Reference по API: [docs/reference/owner_chat_id_resolver.md](../reference/owner_chat_id_resolver.md).
> Как добавить консьюмера: [docs/how-to/add_bot_consumer.md](../how-to/add_bot_consumer.md).
> Тёплый слой про доставку в целом: [telegram_bot.md](telegram_bot.md).

## Проблема, из-за которой всё затевалось

У бота есть один-единственный «адрес владельца» — Telegram `chat_id`, лежащий в файле
секрета тенанта. Раньше `bot/filters.py` читал этот файл **в момент импорта модуля** и,
если файла не было, ронял импорт (`raise` на верхнем уровне). Замысел был правильный —
fail-closed: лучше не подняться вовсе, чем случайно назначить владельцем первого, кто
написал боту. Но у этого решения был неочевидный побочный эффект.

Импорт `bot/filters` тянет за собой почти вся бот-цепочка — `jobs/scheduled`,
`handlers/*`, `telegram_bot`. А значит, любой тест, который эту цепочку импортировал,
на этапе **сбора** (`pytest tests/`) требовал наличия секрета. Пока секрет на месте —
никто не замечал. Но 15 июля 2026 один протекающий тест перекрыл `HEALTH_SECRETS_DIR`
на пустой каталог — и весь сбор упал с тремя collection-error. Утренний гейт покраснел
ложно, хотя код был исправен. Симптом залечили (заглушка одному тесту), но **класс**
остался: fail-closed-на-импорте делает сбор хрупким к утечке переменной окружения.

## Решение и почему именно такое

Резолв стал **ленивым**: `owner_chat_id()` читает файл не при импорте, а при первом
обращении, и запоминает результат (мемоизация). Импорт `bot/filters` теперь не трогает
секрет вовсе — сбор тестов перестал зависеть от того, что кто-то подсунул в окружение.

Fail-closed при этом никуда не делся — он **переехал с импорта на два честных конца**:

- **Старт.** `bot/main.main()` первым делом зовёт `assert_owner_configured()`. Нет
  секрета — бот не поднимается. Тот же принцип «первый встречный не станет владельцем»,
  только теперь он срабатывает при запуске процесса, а не при загрузке модуля.
- **Чтение.** `owner_chat_id()` при отсутствии секрета **бросает исключение, а не
  возвращает None**. Это не педантизм — см. ниже про F2.

Здесь стоит назвать вещь своим именем из теории согласованности: `chat_id` владельца —
это значение с **единственным источником** (single-resolver). Если бы копия этого
значения жила ещё где-то — в локальной константе модуля, в переменной «рядом» — мы бы
получили классический **split-brain**: две копии, пока идентичные, однажды разъезжаются,
и карта владельца уходит не туда (например, партнёру). Поэтому резолвер один —
`bot.filters.owner_chat_id()` — и сторож `test_no_second_owner_chat_id_constant`
запрещает заводить второй путь к значению.

## F2: почему «raise, а не None» — это про безопасность, а не про стиль

По дороге вскрылся реальный баг, который старая архитектура прятала. В
`assessment_bot_handlers.cb_router` owner-проверка была встроена вручную (там
`CallbackQueryHandler`, он не принимает фильтр). Старый код выглядел так:

```
try:    from telegram_bot import OWNER_CHAT_ID
except: OWNER_CHAT_ID = None
if OWNER_CHAT_ID is not None and id != OWNER_CHAT_ID:
    return   # блокируем чужого
```

Разберём, что происходит при недоступном резолве (`OWNER_CHAT_ID = None`). Условие
`None is not None and ...` короткозамыкается в `False` → `return` **не** выполняется →
обработчик продолжает работу для **кого угодно**. Это **fail-OPEN**: при пропаже секрета
дверь не запирается, а распахивается. Причём соседний `handlers/callbacks.py` при None
блокировал всех (fail-closed) — то есть система вела себя несогласованно в зависимости от
того, какой обработчик поймал апдейт.

Именно поэтому `owner_chat_id()` **никогда** не возвращает None: тогда проверка
`id != owner_chat_id()` не может выродиться в «пропустить всех». А в самом `cb_router`
теперь так: резолв недоступен → трактуем как «владелец неизвестен» → **блокируем всех**.
Недоступность адресата — не повод открыть дверь.

## Развилка, которую сознательно отвергли

Правка трогала ядро и пятерых консьюмеров, импортировавших имя `OWNER_CHAT_ID`.
Соблазн был сделать это в несколько коммитов: сначала ядро, потом консьюмеры. Но
деплой здесь — `post-commit push` на Studio, то есть **каждый коммит уезжает в прод
немедленно**. Промежуточный коммит (ядро без консьюмеров) означал бы `ImportError` в
четырёх модулях → бот доставки мед-данных не стартует на каноне до следующего коммита.

Альтернатива «раздельно + PEP 562 shim» (оставить имя `OWNER_CHAT_ID` доступным лениво
через `__getattr__`) не спасала: любой консьюмер, продолжающий импортировать имя на
верхнем уровне, всё равно триггерил бы резолв при своём импорте — то есть **не чинил
заявленную хрупкость сбора**, а сам shim был бы тем самым «вторым путём к значению»,
который принцип запрещает. Поэтому — **один атомарный коммит**: ядро + все консьюмеры +
fix F2 + сторожа сразу. Ни секунды битого прода, без костыля.

## Что честно понимать про пределы

- Мемоизация означает **снимок**: смена `chat_id` (через `--setup`) вступает в силу
  после рестарта бота. Для `chat_id` владельца — величины, не меняющейся в рантайме, —
  это не регресс, а осознанная стоимость (нет чтения файла на каждом auth-чеке).
- «Старт-гейт прошёл» подтверждается строкой `owner resolved: <id>` в логе бота при
  запуске — явная квитанция, что резолв состоялся и на каком владельце.
- Живая проверка кросс-тенант изоляции доставки (владельцу — его карта, партнёру — его)
  требует человеческого глаза; код гарантирует лишь, что резолверы у тенантов разные.
