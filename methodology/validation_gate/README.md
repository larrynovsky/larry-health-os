# Валидационный гейт — методология FDR (провенанс)

Load-bearing методология валидационного гейта корреляций, перенесённая из iCloud в
git 2026-07-12 (СК-1: load-bearing не в iCloud).

## Что здесь

- `fdr_harness.py` — двухступенчатый null-harness статистиков. Stage A: continuous
  oracle с eff-df коррекцией; Stage B: точный циркулярный shift через FFT (пол 1/T).
  Реализует BH и BY (`by_reject` = BH при `q/H(m)`) и discreteness-wall `m·H_m/q`.
- `fdr_sweep.py` — драйвер: сетка m/T/φ, печатает BH/BY power+FDR (300 trials,
  иллюстративно; release требует 50k — §10 вердикта).
- Спека подсистемы — `../signal_validation_lifecycle_SPEC.md` (реестр
  `subsystem_intent.validation_gate.spec` ссылается на неё).
- `validation_gate_FDR_verdict.md` — закрытый внутренний вердикт (final, R1–R6),
  исключённый из публичного экспорта. Ссылки на его § в этом README относятся к
  историческому пересказу ниже; самого документа в публичной копии нет. Доступны
  исходники harness и [спецификация замысла](../signal_validation_lifecycle_SPEC.md),
  но они не заменяют свидетельства квалификации FDR.

## Исторический статус (закрытый вердикт, перенесён 2026-07-12)

Этот пересказ не устанавливает текущий статус выпуска. На момент вердикта
harness был **mechanism proof, НЕ release-grade**: Stage A использовал single-φ eff-df
(вердикт §2/§9: нужна пароспецифичная ACF/спектр), trials скромные, нет partial-null /
mixed-sign / Monte Carlo CI / digital twin. «Harness существует» ≠ «контроль FDR доказан».
Исполнение скриптов требует numpy/scipy; наличие этих пакетов проверяется в окружении
запускающего, а не устанавливается этим документом.

В вердикте предписывался порядок (§1): валидность одиночного p → дискретность → BY →
слой времени (LOND) → классы → воспроизводимая квалификация; изменение `_bh_threshold` в
`correlation_gate.py` откладывалось до готовности Ф0–Ф2. Это исторические условия,
не подтверждение их выполнения в текущем коде.
