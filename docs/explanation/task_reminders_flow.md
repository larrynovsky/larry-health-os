# Задачи и Reminders: откуда берутся и как закрываются

> **Тип документа:** Explanation (Diataxis) — объясняет полный цикл задач.
> Для справочника по таблице tasks: [ARCH_SNAPSHOT.md](../../ARCH_SNAPSHOT.md).

---

## Три источника задач

1. **GP-отчёт** → `task_agent.process_gp_report()` — извлекает задачи из текста отчёта
2. **Автозадачи** → `_auto_create_metric_task()` при emerging_trend или persistent_low
3. **Ручные** → пользователь в Telegram-чате, `db.save_task()` напрямую

---

## Полный цикл: GP-отчёт → macOS Reminders

```
gp_agent генерирует отчёт (текст)
  └── telegram_bot._send_tasks_from_report(report_text)
        └── task_agent.process_gp_report(report_text, "gp_daily")
              └── extract_tasks_from_report()
                    Claude Haiku + TASK_EXTRACTOR_PROMPT
                    Возвращает JSON массив:
                    [{ type, priority, content, deadline, reason, fingerprint }]

                    Типы: question | lab_test | action | followup
                    Приоритеты: critical | high | medium | low

                    Fingerprint — ключ дедупликации:
                    "lab:CEA,CA19.9", "action:BP_week", "lab:CBC"
                    Если такой fingerprint уже в open задачах → пропускается

                    Исключения (из промпта):
                    - Абстрактные советы ("продолжать режим")
                    - Уже запланированные встречи

              └── create_reminders_for_tasks(tasks)
                    → create_macos_reminder(task) для каждой задачи
                    AppleScript → macOS Reminders, список "Health"

                    Заголовок: emoji + content (❓🧪📋🔔)
                    Тело: reason + "\n[task_id:N]"
                    Дедлайн по умолчанию:
                      critical: +1 день
                      high:     +3 дня
                      medium:   +7 дней
                      low:      +14 дней
```

## Носитель выбирается по тому, чем на задачу отвечают (2026-09-12)

Физическое действие закрывается фактом делания — галочка в Reminders может
передать этот факт. Вопрос закрывается ТЕКСТОМ, а галочка текст не несёт.
Закрытие через Reminders или кнопку дашборда без содержательного `resolved_text`
теряет ответ. Даже сохранённый текст бесполезен, если его не читает ни один
потребитель клинического контура: следующий отчёт может повторить тот же вопрос.

Поэтому `question` (как и `assessment`) в Reminders не едет вовсе —
`task_agent.REMINDER_TYPES_EXCLUDED`. Вопрос уходит отдельным сообщением бота с
`ForceReply`; `tasks.tg_message_id` — обратный адрес, по которому реплай находит
свою задачу (образец `pending_field_reviews`). Доставку ограничивает дроссель
`questions.max_per_day` (system_config): канал должен ограничивать поток сообщений.

Ответ принимает ЕДИНСТВЕННЫЙ писатель `task_agent.record_answer`: закрывает задачу
(primary — `tasks.resolved_text`), кладёт производное в `memory_facts` с провенансом
`task:<id>` и ключом = fingerprint вопроса. В GP-контекст ответы едут секцией
`gp_context._build_patient_answers_block`, обрамлённые как слова пациента, а не
инструкция модели.

Закрытие без ответа запрещено САМОЙ БАЗОЙ (`health_db.question_answer_gate_ddl`):
писателей у задачи трое, и проверка в одном из них не стерегла бы остальных.

Перезадавание решает ось времени памяти, а не календарь отчётов
(`task_agent.should_ask_again`): `durable` — не спрашиваем больше никогда,
`standing` — до явной смены, `transient` — по `memory_tuning.transient_ttl_days`.

Вопросы, накопленные в разговоре (`memory_facts(mem_class='question')`), —
кандидаты, а не второй дом: `promote_memory_questions` поднимает их малыми
партиями в `tasks` через гейт «может ответить только пациент».

## Три пути закрытия задачи

### Путь 1 — через Telegram
```
/done <id> [текст] → db.resolve_task(id)
                   → task_agent.complete_macos_reminder(id)
                     osascript: находит ремайндер с "[task_id:N]" в теле
                     ставит completed=true
```

### Путь 2 — через macOS Reminders
```
Пользователь отмечает ремайндер как выполненный
  └── LaunchAgent reminders_sync.py (каждые 3ч)
        osascript → выполненные ремайндеры в "Health"
        regexp: извлекает [task_id:N]
        db.resolve_task(task_id)
```

### Исключение — задача-вопрос (`type='question'`, 2026-09-12)
Пути 1 и 2 к ней не применяются. Закрывает её только ОТВЕТ:
```
реплай на сообщение бота      → tasks_db.get_task_by_tg_message → record_answer
/done <id> <текст>            → record_answer
/done <id> без текста         → бот просит текст
галочка в Reminders           → reminders_sync пропускает (вопросов там и нет)
кнопка в дашборде             → HTTP 409
UPDATE ... status='completed' → RAISE(ABORT) в самой базе
```

### Путь 3 — Dismiss
```
/dismiss <id> → db.resolve_task(id, status="dismissed")
Ремайндер в macOS остаётся (обратная синхронизация отсутствует)
```

### Исключение — задача-опросник (`type='assessment'`, 2026-09-03)
Закрывается ТОЛЬКО заполнением: бот → «📋 Заполнить» (`cb_as:n`) → `assessment_dialog`
→ JSON → `assessment_importer` → строка `instrument:*` в `lab_results` (§16). Дашборд
`/api/tasks/{id}/done` отвечает 409: закрытие задачи без заполнения опросника
не создаёт результата. Независимо придуманный пример: в учебном стенде нажали
«готово», а затем перезагрузили страницу — задача исчезла, но записи оценки нет.
Отложить — snooze, он законен. Доставка — outbox `jobs.scheduled.deliver_unsent_assessment_tasks`
(5 мин, метка `sent_at` по id): он доставляет клавиатуру «Заполнить».

## Почему fingerprint, а не id

GP генерирует отчёты ежедневно. Без дедупликации одна и та же задача
("сдать CEA") появлялась бы каждый день пока не выполнена. Fingerprint
позволяет идентифицировать смысловой дубль независимо от даты создания
или формулировки в отчёте.

## Почему улика судье, а не фильтр «система знает ответ»

Вопрос из памяти может касаться данных, которые уже есть в базе. Независимо
придуманный пример: «какие значения учебного показателя Example_A сохранены?» —
при наличии измерений Example_A в учебном наборе.

Напрашивается фильтр: упомянут аналит, данные по нему есть — вопрос не задаём.
Он был бы неправ, и вот почему. Условный вопрос «вы согласовали дозировку добавки X с врачом?» тоже
упоминает аналит, измерения X тоже есть, а ответ есть только у человека.
Совпадение имени не отличает вопрос о ЧИСЛЕ от вопроса о РЕШЕНИИ.

Поэтому сделано иначе. Правило «вопрос к данным — не человеку» стояло в промпте
судьи с первого дня и не работало не потому, что правила не было, а потому что
судья не знал, есть ли у системы эти измерения. Ему теперь приносят факт:
«в системе УЖЕ есть измерения: <аналит> — N знач., последнее <дата>». Вердикт
по-прежнему выносит он. Второго судьи — списка слов-триггеров — рядом не заведено,
и это не аккуратность, а инвариант `single_judge_of_addressing`: два дома одного
суждения расходятся молча, и в этой подсистеме уже расходились.

**Улика fail-open, и это важнее, чем кажется.** Любой сбой — резолвер имён упал,
чтение лабораторных не удалось — даёт ПУСТУЮ улику, и судья решает как раньше.
Направление выбрано не из осторожности вообще, а из того, как этот канал ломается:
его поломка невидима. Лишний вопрос человек видит и может отклонить. Незаданный
вопрос не видит никто. Закрытый список задач тоже не доказывает, что ответы
дошли до читателя. Между «спросили лишнее» и «промолчали» эта подсистема всегда выбирает
первое; то же правило отдельно записано для сомнения судьи
(`doubt_resolves_into_a_question`).

Граница названа вслух: улика собирается только по лабораторным именам. Метрики сна
и ВСР в неё не входят — их русско-английская карта пока живёт приватной внутри
`monthly_consilium`, и поднимать её в публичный дом это отдельная работа, а не
довесок к этой.
