# Как снять карантин с пары (вынести вердикт)

Рецепт написан ИЗ ИСПОЛНЕННЫХ КОМАНД 2026-07-29 (проба
из рабочих планов, 11 оракулов из 11; сама проба — в закрытой части проекта), а не из головы. Все коды
выхода и тексты ниже — наблюдённые, не предполагаемые.

## Когда это нужно

Пара метрик впервые вошла в pass-set гейта. Это ещё не находка: состав pass-set мерцает, и
одна удачная неделя решением не является. Пара становится `pending_adjudication`, и до
твоего вердикта читатели (конституции, `gp_context`) подают её с пометкой «состав менялся,
ждёт вердикта», а не как связь.

Само это состояние не рассасывается. Стабильный следующий прогон карантин НЕ снимает —
до 2026-07-26 снимал, и это чинили как баг (P1-03).

## 1. Посмотреть, что висит

```bash
ssh Studio
cd ~/health_scripts
python3.11 scripts/adjudicate_quarantine.py
```

Вывод — строки вида:

```
  [pending ] sleep_deep×hrv                   D      вошла 2026-07-29 (0д) эпоха='signal_family_v7'
```

`эпоха` важна: вердикт ложится на пару ВНУТРИ эпохи метода. Смена эпохи (правка
`signal_family`) заново открывает вопрос по всем парам — это не баг, а устройство.

## 2. Посмотреть на числа, а не на список

Вердикт выносится глядя на данные, поэтому CLI, а не кнопка в телефоне. Что смотреть:
сколько прогонов пара держится, менялись ли эпохи, есть ли клиническое объяснение.
`docs/explanation/validation_gate.md` — что вообще означает прохождение гейта.

## 3. Вынести вердикт

Допустить в веру:

```bash
python3.11 scripts/adjudicate_quarantine.py \
    --pair "sleep_deep×hrv" --verdict admit \
    --reason "держится 4 прогона, эпохи не менялись"
```

Отклонить как артефакт:

```bash
python3.11 scripts/adjudicate_quarantine.py \
    --pair "sleep_deep×sleep_rem" --verdict reject \
    --reason "обе метрики производные одного сна, связь тавтологична"
```

**Обоснование обязательно.** Пустое (`--reason "   "`) отвергается кодом выхода 2 —
проверено. Причина — то единственное, что прочитает будущий читатель, когда спросит
«почему эта связь в конституции».

Коды выхода: `0` — записано · `1` — такой pending-пары нет (проверь имя и эпоху) ·
`2` — ошибка употребления · `3` — БД недоступна.

## 4. Убедиться, что вердикт ДОШЁЛ, а не только записался

Это отдельный шаг, а не паранойя: CLI однажды уже был мёртв — звал `resolve_quarantine`
без `method_epoch`, печатал успех и не менял ничего.

```bash
python3.11 scripts/adjudicate_quarantine.py --all
```

Строка должна показать `→ admitted (human, 2026-07-29)`. Но запись в таблице — ещё не
решение, дошедшее до читателя. Полная проверка — следующий прогон:

```bash
python3.11 longitudinal_analysis.py
```

После него в опубликованной вере (`agent_reports`, `agent_type='longitudinal_analysis'`):

- допущенная пара помечена `online_status: "admitted"` — провенанс вердикта;
- отклонённой пары **нет вовсе** — не помечена, а отсутствует;
- пара без вердикта помечена `online_status: "pending_adjudication"`.

Если отклонённая пара появилась находкой без метки — это регрессия VG-R5-01, при которой
человеческое «нет» игнорируется. Она краснеет пробой:

```bash
# на СНИМКЕ канона, не на боевой базе (решение владельца Р-7)
ssh Studio 'cd ~/health_staging && HEALTH_DATA_DIR=~/health_staging \
    HEALTH_SECRETS_DIR=~/health_staging/.secrets_staging \
    python3.11 plans/probe_quarantine_exit_2026-07-29.py --phase live'   # проба — в закрытой части проекта
```

## Чего этот рецепт НЕ покрывает

Он про **выход** из карантина. Как пара туда попадает — путь входа — здесь не описан и
пробой не подтверждён: в прогоне пары ставились в состояние вручную.

И отдельно, найдено при написании: `queue_quarantine` глотает нарушение схемы молча.
Семья вне `CHECK (family IN ('D','A','q_lag'))` даёт `INSERT OR IGNORE` → 0 без единого
сигнала — неотличимо от «пара уже стоит». Сегодня недостижимо, потому что единственный
производитель берёт семьи из ключей снимка pass-set, но связка «ключи снимка = CHECK
схемы» ничем не удерживается.
