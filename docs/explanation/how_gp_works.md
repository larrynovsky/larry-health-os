## Ежедневный цикл (08:30)

```
gp_agent.generate_daily_report(target=today)
  1. Определяет sleep_date=today, activity_date=yesterday
     (Oura пишет сон на дату пробуждения, активность — день назад)
  2. Запускает все 4 LifestyleAgents → briefs dict
  3. Строит GP context (7 дней + тренды + лабы + геном)
  4. Добавляет drift report если есть
  5. Claude Sonnet → generate_daily_report (1 claude call)
  6. _triage_metric() для ключевых метрик:
     emerging_trend или persistent_low → _auto_create_metric_task() (с дедупликацией)
  7. _review_problem_list() фоново после генерации
```

## Еженедельный GP (понедельник 07:00)

```
gp_agent.generate_weekly_report(run_mdt=False)
  1. Читает MDT из agent_reports за последние 3 дня
     (MDT запустился воскресенье 23:00, GP читает воскресенье→утро пн)
  2. _build_gp_context(7 дней)
  3. Добавляет MDT synthesis в контекст
  4. Claude Sonnet (GP_SYSTEM_PROMPT) → report (4096 токенов)
  4a. _guard_absent_claims — сторож «не сдавался» против канона (см. ниже)
  5. _save_gp_report("weekly")
  6. _review_problem_list() фоново
```

### Отсутствие строки читается как отсутствие анализа (2026-08-30)

Лаб-блок врачебного контекста показывает **весь** канон `lab_results` за 730 дней
(~90 аналитов, ~5 КБ), а не ручной список. До 30.08 в `gp_context` жил allowlist
`_GP_KEY_LABS` из 24 имён (с мёртвым ключом `Cholesterol` против канонического
`Cholesterol_Total`). Модель видела только его — и всё, чего в списке не было,
называла «не сдавался»: еженедельный отчёт GP утверждал про несколько аналитов «не
сдавались вообще / никогда / ни разу» — при том что строки этих аналитов в базе были.
Подсказкой служила задача в `problem_list` с `next_action` «проверить <аналиты>» —
модель сложила «задача есть» + «в списке нет» = «не сделано» и повторяла это
несколько недель подряд.

Тот же класс, что и более ранний случай с другим анализом: результат существовал в документе и не доезжал до врача.
Тогда починили вход и добавили три имени в список — второй раз класс проявился на
других именах. Список снят: LLM обязана видеть данные, а не выборку, иначе врёт по
построению.

Два сторожа рядом. `_check_lab_freshness` теперь печатает `⚠ нет данных [medium]`
для теста без строки любого приоритета (раньше medium молча пропускался — аналиты
с encounter-строкой priority=medium не получали ни ✓, ни ❌). И пост-валидатор
`gp_context.absent_claims_contradicted`: фраза «не сдавался / ни разу / не проверен»
в одной клаузе с именем аналита, у которого есть строка в каноне, → один повтор
генерации с явной поправкой, повтор всё ещё врёт → отчёт **не сохраняется**, отказ
в лог ERROR и в возвращаемый текст (`⛔ …`). Сторож судит текст против данных, поэтому
ловит класс целиком — откуда бы вывод ни пришёл (allowlist, устаревший `next_action`,
перенос из прошлого отчёта). Привязка имени к фразе — своя часть клаузы (до/после
`, ` / ` — `), иначе фраза «<аналит A> — никогда не сдавался при повышенном <аналите B>» винила бы
аналит B.

Что ещё всплыло после снятия списка: блок свежести показал просрочку по ряду рутинных
аналитов биохимии (encounter-строки расписания, которых
`seen` из allowlist не видел). Это не регрессия — это то, что было скрыто.

## Логика трендов

### detect_metric_drift() — фиксация устойчивого отклонения

**Метрики:** deep_min, rem_min, hrv_ms, readiness, steps

```
1. Берём 60 дней данных
2. Baseline = среднее за первые 30 дней (≥ 10 точек)
3. Current = среднее за последние 7 дней
4. Threshold = 15% отклонения от baseline
5. Streak = сколько дней подряд отклонение > 15% в одном направлении
6. Если streak ≥ 3 → фиксируем дрейф
```

**Severity:** Mild (15–25%) / Moderate (25–40%) / Severe (>40%)

**Почему streak, а не абсолютное значение:** один плохой день (streak=1) или два
подряд (streak=2) не достигают порога. Система реагирует только на устойчивое
отклонение минимум 3 дня подряд. Разовый всплеск не попадёт ни в один отчёт.

**Куда идёт результат:**
- `generate_hypothesis_from_drift()` — автоматически создаёт гипотезу
- `format_drift_report()` → вставляется в контекст GP
- streak < 3 → не упоминается нигде

### _triage_metric() — классификация для автозадач

Глубже чем drift, работает на уровне отдельных метрик:

- **fluctuation:** |z| < 1.5 и slope маленький → разовый всплеск, задача не создаётся
- **emerging_trend:** slope > 1% от mean за 10+ дней → задача "[AUTO]"
- **persistent_low:** медиана последних 7 дней < 85% исторической медианы → задача "[AUTO]"

## Как GP видит отчёты других агентов

| Кто смотрит | На что смотрит | Что не видит |
|---|---|---|
| GP daily | lifestyle ⚠-флаги через агрегацию | отчёты lifestyle-агентов |
| GP weekly | MDT synthesis | индивидуальные мнения специалистов |
| GP monthly | последние 4 MDT за 35 дней | — |
| MDT специалисты | одинаковый data_package | мнения коллег |
| Lifestyle-агенты | свой домен | GP-отчёты |

Принцип: нет перекрёстного чтения внутри одного уровня. Информация движется
снизу вверх через агрегацию, не через прямой доступ к сырым отчётам.
