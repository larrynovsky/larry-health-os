# What to do when you receive a “tenant encountered a problem” escalation

The message looks like this:

```
🛠 Looks like tenant [health_partner] ran into a technical problem
(confidence 0.80, hypothesis #14).
Signs: echoed_system_text
Judge: the person sent the bot text generated by the system itself
```

## 1. Look at what the person actually sent

```
ssh <studio_ssh> 'sqlite3 ~/health_partner/data/health.db \
  "SELECT created_at, role, substr(content,1,200) FROM conversation_history \
   ORDER BY id DESC LIMIT 6;"'
```

The hypothesis stores only signals — the conversation is deliberately excluded.

## 2. Check whether a storm is happening right now

```
ssh <studio_ssh> 'tail -5 ~/health_scripts/logs/watcher_partner_err.log; \
  launchctl list | grep -E "watcher|bot|dashboard"'
```

## 3. Close the hypothesis with an outcome — required

Without this step, you cannot calculate the false alarm rate, and the threshold cannot be calibrated.

```
ssh <studio_ssh> 'cd ~/health_scripts && PYTHONPATH=. \
  HEALTH_DATA_DIR=~/health_partner \
  HEALTH_SECRETS_DIR=~/.health_secrets_partner \
  /opt/homebrew/bin/python3.11 -c \
  "import service_trouble as st; st.resolve_outcome(14, \"confirmed\")"'
```

`confirmed` means there was a problem. `false_alarm` means there was none. There is deliberately
no third value: free text would make the statistics impossible to calculate.

## 4. View accumulated outcomes

```
ssh <studio_ssh> 'sqlite3 ~/health_partner/data/health.db \
  "SELECT outcome, count(*) FROM service_trouble GROUP BY 1;"'
```

Open hypotheses (`outcome IS NULL`) are those you have not closed. If there are many,
the statistics give a falsely optimistic picture.
